# claude-discord 1.17.0 Implementation Plan: the hook gate by process, the marker sweep, state out of `.claude/`, many bots per project, the removals, and every hook audited

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tests first: each behaviour change begins with a test that fails on `main` (`f4dcdff`) and passes after the change; the commit names the FAIL line it turned. One task at a time, no parallel work.

**Goal:** (1) A `claude -p` started from a bot's Bash is no longer taken for the bot by the plugin's hooks: a hook acts only when its nearest Claude Code process is the bot job's own worker. (2) Markers of sessions that no longer exist (`plugin-sessions/`, `checkin/`, `turns/`) are swept. (3) All bot state leaves `<project>/.claude/discord-agents/` for `~/.claude-discord/projects/<key>/`, running sessions keep working through the move, and a project holds any number of bots with nothing keyed by a bot's name alone. (4) The old install paths go. (5) Every hook is documented and audited per Junyong's rules, and its context cost is measured. (6) The suite's `mstop()` stops calling a slow exit a code failure.

**Architecture:** the gate is one function in `hooks/lib/discord.sh` (`bot_process`), called by `plugin_gate`, cached by the marker `plugin_gate` already writes. The sweep is one function (`sweep_markers`) in a new `bin/lib/state.sh`, fed the listing the start path already fetches. The move is `bin/lib/state.sh` too: `proj_key`, `find_proj`, `move_project`, `unlink_old`, run by `setup`, the start, and the `compat` verb (which the 1.16.0 `update` already calls on the freshly pulled code: that is how the move runs on every machine at its first `update`). The hooks compute `proj_state` and `project_dir` once in `discord.sh`.

**Tech Stack:** bash 3.2-compatible, jq 1.6, BSD userland, the suite's stubs; Python 3 + Textual for the TUI (one path).

Base: `main` at `f4dcdff` (1.16.0). Branch: `feat/state-1.17.0`.

**Scope (decided on Discord 2026-10-16 with junyong-dev-bot and Junyong; not reopened here):** items 1-8 of the brief. This plan adds only how, where (file:line on `f4dcdff`), what was measured, and the few choices the brief left open, each marked **owner decision**.

### The gate, measured (Claude Code 2.1.301, read from the binary and from the 9 live sessions here)

- `~/.claude/sessions/<pid>.json` is written by every TOP-LEVEL session at registration and rewritten in place on a status, name, cwd or session-id change (`updatePidFile`), deleted on exit (only a SIGKILL leaves one). Keys: `pid sessionId cwd startedAt procStart version peerProtocol peerFeatures kind entrypoint pidDomain messagingSocketPath name nameSince nameSource jobId updatedAt status statusUpdatedAt bridgeSessionId [agent]`. `jobId = kind == "bg" && CLAUDE_JOB_DIR ? basename(CLAUDE_JOB_DIR) : undefined`; `kind = CLAUDE_CODE_SESSION_KIND ?? "interactive"`. `procStart` is field 22 of `/proc/<pid>/stat` (checked equal): a pid-reuse guard for free. All 9 here: `kind bg`, `entrypoint cli`, all alive, none stale.
- **A child writes none**: registration is skipped when `CLAUDE_CODE_CHILD_SESSION` is set, and every Bash tool and hook environment has `CLAUDE_CODE_CHILD_SESSION=1` (this session's Bash: `1`). The worker strips `CLAUDE_CODE_SESSION_KIND` and `CLAUDE_BG_*` from tool environments but keeps `CLAUDE_JOB_DIR`, which a child inherits.
- **`/clear` and compaction keep the pid**: the same process, `updatePidFile({sessionId: new})`, `jobId` untouched (job `6788a2bf` here: `state.json`'s `sessionId` is the first one, the pid file's `sessionId` is the current `fa8700a9...`, `jobId` stays). **A respawn** is a new worker process: the current dong-dev-bot worker 2574208 is a `claude --resume .../199eeafe-....jsonl` started ~2026-10-15T22:40Z with a new pid and `jobId` still `199eeafe`, its own pid file. The daemon log prints no worker pids (`bg adopt: adopted=10 respawned=0`, `respawned 1/2 stale workers`).
- Process tree of a hook: `bash <hook>` <- `/bin/sh -c "<cmd>"` (dash) <- the worker (`claude`, has the pid file): 2 hops. A `claude -p` child's hook: `bash <hook>` <- `sh` <- `claude` (the child, **no pid file**) <- the bot's Bash tool `bash -c` <- **the bot's worker** (the pid file with the bot's `jobId`): 4 hops. A miss walks ~10 hops (`claude-proxied` wrappers, `--bg-pty-host`, `daemon run`) to pid 1.
- **So the walk as agreed gives a false positive on exactly the case it is for**: the child's hook walks past the child (no file) and finds the bot's worker with the bot's job id. "The first ancestor that has a pid file" fails the same way. Stopping at the nearest ancestor whose `comm` is `claude` would work only while the binary is called that (a `node cli.js` child shows `node`).
- **`CLAUDE_PID`** is in every hook's and tool's environment: the pid of the Claude Code process that spawned it, set per process (`O5e()`: `CLAUDE_PID: String(process.pid)`, 2.1.299 and 2.1.301), so a child overwrites it with its own pid. This session's Bash: `CLAUDE_PID=2574208` = dong-dev-bot's worker. Undocumented (risk 1).
- **`pinned-job` is missing for 3 of 6 live bots here** (dong-cswap-bot `805313d9`, photo-bot `01e4cdac`, dataset-viewer-bot `c521ce4f`): on-session-start removes it when the job was pinned by someone else (`hooks/turn/on-session-start:120-124`: "someone else pinned this job"; cswap pins jobs). A gate on `jobId == pinned-job` would silence half the bots on this machine.
- A foreground bot's pid file has `kind interactive` and no `jobId`.
- Timing (container, bash 5.1, fork-free: `read` of `/proc/P/stat`, the field after the last `) `, a bash regex on the pid file): walk hit at 1 hop 0.63 ms, at 5 hops 1.0 ms, full miss (10 hops) 1.5 ms (~0.15 ms/hop); `$(<f)` instead of `read -d ''` +0.4 ms (it forks); **the direct check `sessions/$CLAUDE_PID.json` + `procStart` 0.47 ms**; `ps -o ppid=,comm= -p` 5.4 ms per call (what a Mac walk would need per hop); `jq -r .jobId` 2.2 ms; exec of `/bin/true` 0.7 ms. The Mac (`ssh -p 50022 localhost`) refused the connection from the container and the host today: no Mac numbers; the direct check forks nothing on either OS.
- Markers here: 2 per bot dir, all 12 the bots' own sessions (transcript `entrypoint: cli`); 40 of 243 transcripts are `sdk-cli` (children run here, their hooks left no marker in these dirs yet). `checkin/` 12 files (project level), `turns/` 30 files over 6 bots. The 634-marker pile is the peer's.

## Task 1: the hook gate by process (1.17.0; tests first)

**Owner decision 2 (the signal).** The agreed design was an ancestor walk to the job's worker matched on `pinned-job`. Measured above, it is wrong twice: the walk passes through the child to the bot's worker (false positive for every child), and `pinned-job` is absent for 3 of 6 live bots here (false negative for the bot). **Recommended:** the hook's own Claude Code process decides: `$CLAUDE_PID` names a pid whose `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/sessions/$CLAUDE_PID.json` exists (a top-level session: children never register), and on Linux that file's `procStart` equals field 22 of `/proc/$CLAUDE_PID/stat` (pid reuse); when the file carries a `jobId`, it equals `${CLAUDE_JOB_DIR##*/}` (a background worker of this very job; a foreground bot's file has no `jobId` and passes on the first two). No walk, no fork, 0.47 ms, the same on macOS (no `procStart` check there: a pid file outlives its process only after a SIGKILL, and pid reuse on top of that is the one gap). `CLAUDE_PID` unset (a Claude Code that stops setting it): **fail open**, today's behaviour (a child acts as the bot again), never fail closed (every bot silent). Alternative A: the walk, stopping at the first ancestor whose `comm` is `claude` (works today; a renamed binary or `node cli.js` breaks it: fail-open then too; 1 ms Linux, 2-4 `ps` forks per event on a Mac). Alternative B: as agreed (do not: measured wrong).

**Files:** `hooks/lib/discord.sh` (`plugin_gate` :147-190), `test-claude-discord.sh` (a seam at the top, the gate cases beside the plugin-gate cases at :1675-1860), `README.md` (Hooks: who is the bot).

### 6.3 The prompt cache (rule c; https://code.claude.com/docs/en/prompt-caching, fetched 2026-10-16)

The doc: "The match is exact, so a change anywhere in the prefix recomputes everything after it"; system prompt (tools, core instructions) / project context (CLAUDE.md, memory, unscoped rules, re-read at start, `/clear`, `/compact`) / conversation (every turn); "A change to the conversation layer leaves the system prompt and project context cached". Its list of actions that invalidate the cache: "Switching models · Changing effort level · Turning on fast mode · Connecting or removing an MCP server · Enabling or disabling a plugin · Denying an entire tool · Compacting the conversation · Accumulating many images · Upgrading Claude Code".

- **The hooks' additionalContext** (SessionStart, UserPromptSubmit) and **deny reasons** are conversation rows appended after the cached prefix: they invalidate nothing; they cost their bytes once. A re-injection (on-prompt after a text change) costs its bytes again, no cache miss: the 41 reorder re-injections were a token cost, not a cache cost.
- **`update`** (a `git pull`, no reload): nothing in the prompt changes; hook scripts run from disk at their next event. A changed identity text re-primes once per session (17 measured re-injections after updates).
- **`/reload-plugins`**: "Claude Code never invalidates the cache for a plugin's skills, commands, agents, hooks, monitors, or themes. It appends their content after the existing conversation"; an MCP-providing plugin follows the MCP rules (with tool search, the default, "Claude Code keeps the tool list from the conversation's first request"), and a reload that would force a full re-read is refused with a warning (`--force`). Ours declares no MCP server; the official discord plugin's server is unchanged by a reload unless its config changed (the patch edits `server.ts`, not the MCP config). So the `update` message's advice costs no cache. It is needed only when `hooks.json` changed (owner decision 4 changes it in 1.17.0: say so in the update line).
- **`--append-system-prompt`** is in the system layer: fixed per session, so harmless; it changes only with a new session.
- **`--settings` with `enabledPlugins`** is passed at launch only; enabling or disabling a plugin mid-session would invalidate everything, and nothing here does that.
- **Upgrading Claude Code** invalidates (the daemon's self-upgrade respawns workers): not ours.

# claude-discord 1.12.0 hosts management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A manager bot's hosts ledger is changed with a command, `claude-discord hosts list|add|rm|laptop|set`, and from the TUI's Configuration tab, which drives that command: `+ Add host` / `a` (a search over `~/.ssh/config`) and a per-host settings popup on Enter.
**Architecture:** One new verb in `bin/claude-discord` edits `<bot dir>/hosts` with shell builtins only, under a lock and by rename, keeping every byte it does not change; `add` first asks the host who it is over one ssh call (`--version --host-id`: safe on every older version) and refuses a host that is this same home, using a per-home `~/.claude-discord/host-id` and a per-manager `watchers/<manager>` record on the checked host. The monitor gains one front, `monitor --check`, that asks the running monitor for a pass now. `tui/claude_discord_tui.py` stays one file: new pure functions read `~/.ssh/config` as text, and two modal screens (`AddHost`, `HostEdit`) run the CLI in worker threads; the TUI never reads or writes the ledger itself and never holds an env value it did not just get typed.
**Tech Stack:** bash (3.2-compatible: macOS `/bin/bash`), jq (1.6 on the slower machine), perl (flock, the ssh cap), ssh; Python 3.9+ with Textual `>=8.2.8,<9` and rich through `uv run --script` (TUI only); the stub-only suite `test-claude-discord.sh` and the pilot tests `tests/tui/test_tui.py`.
**Spec:** docs/superpowers/specs/2026-10-12-tui-redesign-hosts-access.md (sections "Owners' requirements", "1.12.0: hosts management (write)", "Constraints"); mocks `docs/superpowers/specs/2026-10-12-tui-mocks/mock-addhost.png`, `mock-edithost.png`, `mock-config.png`.

## Global Constraints

- **Scope.** Exactly the spec's "1.12.0: hosts management (write)" and the three mocks, plus one fix to shipped 1.11.1 behaviour that the coordinator added while this plan was written (Task 7: the Bots table's status column). Nothing of 1.13.0 (access and token editing, the `e` key, bot mode or bot name editing), the `f`/`F` fix keys or the manager band is built or prepared: no task adds a hook, a field or a flag "for later". The "display name" this plan edits is a HOST's ledger `name=` word (spec 1.12.0), not a bot's name.
- **Execution is native:** one implementer does Tasks 1 to 11 strictly in order, each ending in a commit with its tests passing; then ONE deep review of the whole branch (`git diff main...feat/hosts-1.12.0`) by a separate review agent; then a verification on another machine (jq 1.6 and 1.7, bash on Linux). No parallel tasks.
- **Suite:** `./test-claude-discord.sh ./bin/claude-discord` stays under 40 s wall, run serially, stubs only (no real claude, `claude -p`, `--bg`, network or Discord; ssh is the suite's stub at `$HOME/bin/ssh`, which Task 4 teaches `--`). It sits at about 30.5 s here and 32.8 s on the reference machine. This plan may add at most 2.5 s in total; each task states what it adds, and measured in the scratch copy the blocks sum to 2.25 s (Tasks 1 to 5: 0.2 + 0.35 + 0.35 + 0.5 + 0.5; Task 10: 0.35) and whole runs differ by 2.40 s: 0.1 s inside the budget, so a task that adds a test case beyond this plan's must take one out. TUI behaviour is tested in `tests/tui/test_tui.py` (Textual's pilot), never in the suite: 38 `ok:` lines and about 13 s before this plan, 46 and about 23 s after it; it must stay under 25 s.
- **Secrets.** No token and no env VALUE in `state.json`, `monitor.log`, the TUI, a posted message, or the argument list of any process this plan starts. The TUI never reads a `.env`, never reads the ledger file, and gets env KEY NAMES only (`hosts list --json`). A value the user types reaches the ledger on the stdin of `hosts set <alias> --stdin`. The CLI never echoes a word it refuses. See disagreement 1 below for the two places where a value is in an argument list today and what this plan does about each.
- **Untrusted text.** Everything that came from another machine (an ssh answer, a watcher record, a host's health document) or from `~/.ssh/config` is data: in the CLI it is cut, stripped of control characters and only matched against a regex, never evaluated and never a word of a command; in the TUI it passes `clean` before it is drawn. Every write goes through the CLI. A wrong-typed JSON from `hosts list --json` must not raise in the TUI.
- **ssh.** An alias reaches ssh only after `h_alias` (or `ALIAS` in the TUI) and always after `--`. Every ssh call has `BatchMode=yes`, `ConnectTimeout=8`, stdin from `/dev/null` and a cap on the whole call; in the TUI every call that can block runs in a worker thread.
- **bash 3.2:** `bin/claude-discord` and `monitor/monitor.sh` must parse and run under macOS `/bin/bash` 3.2: no `${var,,}`, no `mapfile`, no associative arrays, no `case` inside `$(...)`, no quoted jq program inside `"$( )"` inside double quotes. The ledger is edited with shell builtins only (no sed, awk or GNU-only flag in the edit path). `monitor/monitor.sh` has no here-document and no here-string (`<<`) at all. The suite itself is Linux-only; its own `bash4_lint` covers the wrapper and the monitor.
- **jq:** functions of jq 1.6 only. No new jq start on a per-prompt or per-tick path: the one new jq call is in `hosts list --json`, run on demand.
- **No OS scheduler** (no launchd, systemd or cron).
- **Style:** code and comments in English; match the surrounding style (long lines and dense why-comments are the house style in the shell files). Minimum code: no abstraction for a single use, no configurability nobody asked for. Labels in the TUI are English. Checkboxes anywhere in the TUI are drawn `[✓]` / `[ ]`, radio choices `(●)` / `( )` (this plan draws one radio pair and no checkbox).
- **HARD HOME RULE** (from `CLAUDE.md`): any probe outside the test suite sets a literal sandbox `HOME` in the SAME Bash call, chained with `&&`; never write the real `~/.claude.json`, `~/.claude`, `~/.claude-discord` or `~/.local/bin`, nor any `.env`. Do not start the real TUI, a real monitor or a `claude` session to "see" a change: the pilot tests and the suite are the checks. Note that OpenSSH finds `~/.ssh/config` through the password database, not `$HOME`: a sandbox `HOME` does not sandbox a real `ssh`, so never run the real ssh against a host in a probe.
- **Commits:** by explicit path (`git commit -m … -- <paths>`; no file is new, so no `git add` is needed), on branch `feat/hosts-1.12.0`, with no `Co-Authored-By` line. Never push to `main` from this plan's steps.

## Review Focus

The five input classes most likely to bite a user, most likely first. Each names the test that pins it; a reviewer should see that test fail when the fix is reverted (the mutation that was run for each is in "What was run").

1. **The same machine twice, and removing what must stay.** The first thing an owner on lmd79 will try is to add the host from inside its container (`ssh localhost`): the same `$HOME`, so every bot would be reported twice, one side `down`. Likewise a second alias for a host already listed, `rm local`, and removing the last host. Pinned in Task 4 (suite: `FAIL: a host that answers with this home's host-id is the same home`, exit 4), Task 5 (`FAIL: a host this manager already checks under another alias is the same home`; `FAIL: this manager's own record under an alias no longer listed … is no obstacle`), Task 3 (`FAIL: rm local is refused (exit 2)`; `FAIL: removing the last other host leaves the ledger in place with local`) and Task 4's host-id block (`FAIL: eight first --version --host-id calls at once must all print the one id that was kept`).
2. **A host that does not answer, hangs, or answers something else, when it is added.** Laptops are asleep, a bastion drops, a shell rc prints a banner. `add` must end within its cap, read at most 4096 bytes, trust none of them, and the TUI must stay alive meanwhile. Pinned in Task 4 (`FAIL: an unreachable host is not added`; `FAIL: a probe that hangs is ended by the cap` and `FAIL: a hung probe must end at its cap, its ssh killed`; `FAIL: an answer is read up to 4096 bytes and no further`; `FAIL: a host whose claude-discord is older than 1.12.0 is added with a warning …`, which also checks that no escape sequence of the banner reaches stderr) and Task 8 (pure: `run_capped` returns 124 inside 2 s with a grandchild still sleeping; pilot `add_host`: `info() == "checking lmd_dkim ..."` while the stub's add sleeps, and the exit-5 path's third Enter).
3. **An env value seen where it must not be.** A proxy URL can hold a password. Pinned in Task 1 (`FAIL: hosts list must never print an env value`), Task 2 (`FAIL: '…' is no word of a ledger line: exit 2, nothing written, the word not echoed`), Task 3 (`set --stdin`: the value arrives on stdin; `[[ $HO != *pw2* ]]`), Task 9 (pilot `host_edit`: `"s3c" not in drawn(app)` while it is typed, the stub's stdin file holds the values and `"s3" not in (d / "args").read_text()`) and Task 11's gates (the TUI opens four kinds of file, none of them a `.env` or the ledger).
4. **A word nobody should have typed, and a configuration nobody should have written.** An "alias" that is an ssh option (`-oProxyCommand=…`) or holds shell metacharacters, a quote, `#`, `=`, a control character; an `~/.ssh/config` with a cycle of Includes, `Match exec`, CRLF, bytes that are no UTF-8, a FIFO, megabytes. Pinned in Task 2 (`FAIL: '…' is no ssh alias: exit 2, nothing written, no ssh, no escape sequence echoed`), Task 4 (`--` before the alias: `FAIL: add runs the command --dry-run printed …`), Task 5 (`FAIL: --watch '…' has a word of the wrong shape`), Task 6 (`ok: ~/.ssh/config is read as text: …`, whose fixture has all of the above and fails the test if any command is run) and Task 8 (pilot `add_host`: `What is no alias is no candidate, and Enter on it runs nothing`; pure: `ssh -G` is asked with `--` before the alias).
5. **Two writers of the ledger at once, and a monitor reading it mid-write.** A TUI save while `hosts set` runs in a shell; a pass that starts during either. Pinned in Task 2 (`FAIL: an add started while another writer holds the ledger's lock waits and adds to that writer's version`; `FAIL: the ledger is written to a temp file and moved in (mode kept, no temp left …)`), Task 3 (`FAIL: set --stdin applies every line of stdin in one write`; `FAIL: a change that is already so is said and writes nothing`), Task 9 (pilot `host_edit`: Save is exactly one `hosts --bot mgr set wmac --stdin` call) and Task 10 (suite: the pass `monitor --check` asks for reads the ledger as it is then).

## Where the spec, the mocks and the code disagree, or the spec is silent, and what this plan does

Most consequential first. File and line numbers are of `main` at `451e359` (1.11.1).

1. **"No env VALUE in the argv of any process" cannot be met as written, and is not met today.** The spec's own syntax puts values on a command line (`add <alias> [laptop] [KEY=VALUE...]`), and the monitor passes every ledger value in ssh's argument list for the whole of each pass (`monitor/monitor.sh:776`: `remote="env $(printf '%q ' "${envs[@]}")…"`, run at `:483`) and in `env`'s for the local host (`:481`). This plan: everything it ADDS that carries a value on behalf of the TUI uses stdin (`hosts set <alias> --stdin`); the CLI's argv forms stay, as the spec writes them, for a person at a shell, and the README says where that value then is; the CLI's own edit path starts no child with a value (builtins only). The monitor's two lines are NOT changed: that is the monitor's remote command, outside the 1.12.0 section. The owner should decide whether a later release moves them to stdin.
2. **How the remote host-id is read.** The spec: "probes `ssh -o BatchMode=yes <alias> '~/.local/bin/claude-discord --version'` and reads the remote host-id", with no word on how. Chosen: `--version --host-id` (Task 4). A claude-discord before 1.12.0 exits right after its version line whatever follows (`bin/claude-discord:1872-1875`), so the probe is safe on every version; a new verb would be read by an older wrapper as a bot name and reach the launcher (`:2041`). For the same reason the watcher record is written and removed with `--version --watch` / `--unwatch`. The command also differs from the spec's and the mock's line by `-o ConnectTimeout=8` and `--`.
3. **A host with no claude-discord, or one that does not answer.** The spec does not say. Chosen: not added, exit 5, with `--no-probe` named as the way to add it unchecked (Task 4); in the TUI a third Enter does that (Task 8). Adding it silently would post `[blind]` or `[hostdown]` to the shared channel for a host with nothing to check. **An older claude-discord (no host-id): added with a warning.**
4. **"Same as … a listed host" has nowhere to look.** No file holds the host-ids of listed hosts, and the ledger's format may not change. Chosen: the host's own `watchers/<this manager>` record, written by this home under another alias that is still in the ledger (Task 5). It covers hosts added with `hosts add`. A line written by `setup` (`bin/claude-discord:505-545`, which probes for a battery, not for an id) or by hand has no record, so a second alias for such a host is not caught; `setup` is not changed (the spec gives the probe to `add` only).
5. **`rm` when the host is unreachable.** The spec: "`rm` deletes it". Chosen: the ledger line goes first and `rm` exits 0; the record's removal is tried, capped, and a failure is a warning that names the command to run later. A stale record only makes another manager's `add` warn (Task 5).
6. **What `host-id` identifies on a shared home.** One id per HOME (`~/.claude-discord` is in it), so lmd79's host and its container have the same id (`README.md:967-978`). That is the intended refusal, not a collision (Task 4).
7. **Check now.** The spec says "buttons Check now" and nothing else. Chosen: it asks the running monitor for a pass (`monitor --check`, a marker the tick sees), probes nothing itself, starts nothing, posts nothing; and the TUI asks the same after every change it makes to the ledger (Task 10). This touches `monitor/monitor.sh`, which the 1.12.0 section does not name: 4 lines of behaviour and a front.
8. **Which manager, from a session that is not a dev-manager's project.** The spec is silent. Chosen: as `tui` and `monitor` resolve it (`bin/claude-discord:1958-2016`, `:1930-1950`): the project above the cwd, else the recorded projects, exactly one, never asked for. So on a machine with one manager, `claude-discord hosts rm x` from another bot's project changes that manager's ledger; every change prints the ledger's path (Task 1).
9. **The mocks draw `x remove (asks) · l laptop on/off` and the footer keys `x`, `l`; the spec's 1.12.0 text names only `a` and Enter.** Built (Task 9): the owner's scope is "the spec's 1.12.0 section and the mocks". Each is one CLI call.
10. **Enter on a host row used to show its raw fields and recovery command** (`tui/claude_discord_tui.py:828-832`); the spec gives Enter to the popup. The popup shows the reach, the reason and the recovery command; the raw-fields screen stays for a host that left the ledger (nothing to set) and for a state entry that is no object (Task 9).
11. **`+ Add host` is drawn as a button and is not one.** The TUI has no mouse target anywhere (one pane, a row cursor). It is a label above the table, pressed with `a` (Task 8).
12. **The picker's rows and its probe line are not the mock's letter for letter.** The mock: `enter checks it first:  ssh -o BatchMode=yes lmd_dkim '~/.local/bin/claude-discord --version'`, `4 matches`, and `via ProxyJump bastion` for a host with no HostName. Built: the CLI's real line (choice 2); the count is of configuration matches, and the alias as typed is one more row under them; a target is always `user@host:port`, with ` · via <jump>` after it (the same text the popup's target shows).
13. **The popup's env line.** The mock: `none   + add KEY=VALUE (a proxy this host needs to reach Discord)` on one line. Built: the list of keys (`KEY ••••`) and under it two fields, KEY and its value, since a value must be masked while typed and one field cannot mask half of itself (Task 9).
14. **A display name with a space** cannot be a ledger word (`monitor.sh:763` would read `name=my box` as `my`). Refused (exit 2), not rewritten (Task 2); the TUI's field takes no whitespace.
15. **A duplicate alias** (two lines for one host): `set` and `laptop` change both, `rm` removes both, `add` refuses, `list` shows both (Task 3). The spec does not mention it.
16. **`rm local`** is refused; **the last other host** can go and the ledger file stays (Task 3). The spec does not mention either.
17. **`hosts` becomes a reserved bot name** (`bin/claude-discord:748`). A bot already named `hosts` (none is known) is still started with `--name hosts`; `claude-discord hosts …` is the verb now (Task 1).
18. **The status column (Task 7, the coordinator's item):** its least width is 15, not the widest status alone (`● ok` is 4), so the notes under an opened row fit a line; only CLOSED rows are measured, so opening a row moves no column; a reason wraps on five lines of 15 instead of three of 25; and the bot column grows for a long name with NO mode too (a 22-cell Hangul name was cut at 16 at any width). Seven existing assertions pin the old layout and are changed there.
19. **The suite's ssh stub** (`test-claude-discord.sh:3534`) read `--` as the host; one word is added to its option loop (Task 4).
20. **The README is changed in the last task**, not in the task that changes what a passage describes (the 1.11.0 plan's habit): the owner's order for this plan.
21. **Decision 5 (`[✓]` / `[ ]`):** none of the 1.12.0 screens has a checkbox; the kind is a radio pair, drawn `( ) server   (●) laptop`.
22. **`~/.ssh/config` is found through `$HOME`** (`Path.home()`), where OpenSSH uses the password database. They differ only in a sandbox; the tests pass the home in.
23. **An `Include` inside a `Host` block** is read as if at the top level, and one inside a `Match` block is not read at all (Task 6): candidates and their targets are a display, and `ssh -G` on the chosen alias shows what ssh will do.

`--no-probe` is parsed here and does nothing yet: Task 4 makes the probe the default, and the cases of this task and the next already pass the flag, so they do not change when the probe arrives.

Choices, each with its reason:
- **An alias** is what the monitor's pass accepts as a host (`monitor/monitor.sh:757`): letters, digits, `.`, `_`, `@`, `-`, not starting with `-`, 255 characters at most. Anything else would be a line the monitor skips, and a leading `-` would be read by ssh as an option. So whitespace, `#`, quotes, `=`, `/`, `;`, `$` and control characters are all refused by the one character class. A word starting with `-` never gets as far as being an alias: the option loop refuses it (exit 2), and there is no `--` to end the options.
- **A KEY** follows the shell identifier rule (the monitor's own test, `monitor.sh:764`), 64 characters at most. `name` (lower case) is the display-name word.
- **A VALUE** may not hold whitespace or a control character (a ledger word ends at the first space: the monitor would read the rest as other words) nor a quote, single or double (the ledger has no quoting, so `K="v"` would send the quotes as part of the value: almost always a pasted shell line). `#`, `$`, backslash and a leading `-` are allowed: the monitor reads a word literally, quotes it for the remote shell with `printf %q`, and treats `#` as a comment only at the start of a line. 1024 characters at most; a display name 64.
- **A display name with a space is refused, not rewritten** (`name=my box`, exit 2): the ledger word cannot hold one, and a silent `my-box` would not be what was typed.
- **No word of the caller is ever echoed** in an error, only a key once it is known to be one: `hosts add h1 http://user:pw@proxy` (the key forgotten) must not put the URL in a terminal scrollback or the TUI.
- **One writer at a time**: `flock` (through perl, as the monitor's lock) on `<ledger>.lock`, taken before the ledger is read and held until it is renamed in. The kernel drops it when the process dies, so it is never stale; a second writer waits up to 5 s, then exits 1 having changed nothing. The ledger itself cannot be the lock: it is replaced by rename, so two writers would lock two different files.
- **Never truncated in place**: temp file in the ledger's directory, the ledger's own mode, `mv -f`. A monitor reading mid-write sees the old file or the new one. `write_hosts` already did this; its three lines become `ledger_write`, used by both.
- **Lines that are not changed keep their bytes** (comments, blank lines, CRLF endings, the spacing between words, words the monitor skips). A missing newline at the end of the file is added.

What each does, exactly:
- **`set <alias> KEY=VALUE`**: on every line of `<alias>`, the first `KEY=` word is replaced where it stands and any later `KEY=` word of that line is dropped (so the line holds the key once, and what `env` would have used, the last one, is no longer ambiguous); with no such word, `KEY=VALUE` becomes the line's last word. - **`set <alias> KEY=`** removes every `KEY=` word of the line. Removing what is not there is no change (exit 0).

- **`rm <alias>`** removes every line of `<alias>`. The monitor keeps the host for a day as "left the ledger" (`left_s`), frozen with its bots, then drops it: nothing is posted either way.
- **A duplicate alias** (two lines for one host: the monitor runs the host twice and the second line wins in `state.json`): `set` and `laptop` change every line of it, `rm` removes them all, `add` refuses (exit 3). `list` shows each line.

- **An alias that is not there** is exit 3 for `set`, `laptop` and `rm`, nothing written.
- **A changed line** is written with one space between its words and keeps its CRLF if it had one. A line whose words come out the same (the change was already so) keeps its bytes, and when no line changes nothing is written at all.
- **`--stdin`** is how a value reaches the ledger without being in any process's argument list: the TUI's Save sends every change of a host as one `set <alias> --stdin` call, so a save is one rename (all of it or none). Choices, each with its reason:
- **`host-id` names a HOME, not a machine.** What a monitor pass reads on a host is that home's `~/.claude-discord/records/projects`, so two ledger lines that reach one home report every bot of it twice. lmd79's host and its container `dy-dev` share `$HOME` (README, "A host and a container that share `$HOME`"): they have one `host-id`, and that is the rule working, since `ssh localhost` from the container is exactly the line that must be refused (its bots run in the container and would all read `down` from the host side). - **Created once, atomically.** The id is written to a temp file and hard-linked to `host-id`: `ln` fails when the name exists, so of two processes creating it at once one wins and both read the winner's. A `host-id` that is there but is no id (cut off, hand-edited) is replaced by rename; two processes repairing a damaged file at once may each print a different id for that one call, which nothing here guards against.
- **The probe rides on `--version`.** The spec's command is `ssh -o BatchMode=yes <alias> '~/.local/bin/claude-discord --version'` "and reads the remote host-id". A claude-discord before 1.12.0 prints its version line and exits whatever follows `--version` (`bin/claude-discord:1872`), so `--version --host-id` is safe on every version. Any NEW verb is not: an older wrapper reads an unknown first word as a bot name and goes on into the launcher (`bin/claude-discord:2041`, the 1.11.0 review's I4 shape).
- **The command, exactly:** `ssh -o BatchMode=yes -o ConnectTimeout=8 -- <alias> '~/.local/bin/claude-discord --version --host-id'`. `ConnectTimeout=8` as the monitor's pass; `--` ends ssh's options, so even an alias that got past `h_alias` could not be read as one. - **A cap on the whole call** (`CLAUDE_DISCORD_PROBE_CAP`, 20 s): `ConnectTimeout` bounds the connection only, and a remote shell or a ProxyCommand can hang after it. ssh runs in its own process group under a perl parent that kills the group when the cap is reached (no `timeout(1)` on macOS; the same reason the monitor polls). stdin is `/dev/null`.
- **The answer is untrusted.** It comes from another machine (and from whatever its shell rc files print). At most 4096 bytes are kept (`head -c`; a host that prints megabytes is cut off and ssh dies of the closed pipe), NUL bytes are dropped, each line loses its control characters and is cut at 200 characters before anything is done with it, and the only thing done is `read` into variables and a regex match: the version must be `N.N.N`, the id 32 hex digits. Nothing is evaluated, and no word of it becomes part of a command. The one line quoted back to the user (ssh's last, as the reason) is that cleaned, cut line.
- **Refused: the same home** (the answer's host-id is this home's): exit 4, `same home as local`, nothing written.

- **`add local`** (a ledger that lost its `local` line) asks nobody: `local` is this machine.
- **Asked before the lock, written under it.** The probe can take seconds; the ledger's lock is held only while it is read and renamed. An alias already listed is exit 3 before any ssh, and `h_edit` checks again under the lock.

**Files:**
- Test: `test-claude-discord.sh` (below Task 4's `ok: host-id is made once …` line)
- Modify: `bin/claude-discord` (`--version` gains `--watch` and `--unwatch` and lists the watchers after `host-id`; `h_ask` reads them; `hosts add` decides on them and writes its own; `hosts rm` removes it)

**Interfaces:**
- Consumes: `host_id`, `hid_re`, `h_ssh`, `h_ask`, `h_has`, `h_edit`, `h_probe` (Tasks 2 to 4).
- Produces:
  - `~/.claude-discord/watchers/<manager>` on a checked host: one line, `<host-id of the manager's home> <the manager's alias for this host> <UTC time written, YYYY-MM-DDTHH:MM:SSZ>`, mode 600 in a 700 directory. The file's name is the manager bot's name.
  - `claude-discord --version --host-id` prints, after `host-id <id>`, one `watcher <manager> <host-id> <alias> <time>` line per file.
  - `claude-discord --version --watch <manager> <host-id> <alias>` writes that manager's file and prints `watched <manager>` (exit 2 on a word of the wrong shape, exit 1 when `<host-id>` is this home's own or the write failed).
  - `claude-discord --version --unwatch <manager> <host-id>` removes the file when its first word is `<host-id>` and prints `unwatched <manager>`.
  - `hosts add`: exit 4 `same home as <alias>`; a warning `already watched by <manager>`; after the ledger is written, the `--watch` call. `hosts rm`: after the ledger is written, the `--unwatch` call. `h_ask` also sets `h_watch` (one `<manager> <host-id> <alias> <time>` a line); `mgr_re` and `alias_re` are the regexes of a manager name a watcher file can carry and of an alias.
- Suite time: +0.5 s measured (25 wrapper starts, 14 of them with one or two stub ssh calls).

Choices, each with its reason:
- **Two ssh calls on `add`, one on `rm`.** The probe (Task 4) only reads; `--watch` is sent after the ledger has the line, so a watcher file exists only for a host that is, or was, in a ledger. A failed `--watch` is a warning: the host is added and checked all the same.
- **"Same home as a listed host"** is known from the host's own records: its `watchers/<this manager>` file, written by this home (the file's host-id is ours) under ANOTHER alias that is still in this ledger, means this home is already checked under that alias: exit 4, `same home as <alias>`. A record whose alias is no longer in the ledger is stale (see `rm` below) and is overwritten. This covers hosts added with `hosts add`; a line written by `setup` or by hand has no record on its host, so a second alias for it is not caught. The README says so.
- **"Already watched by `<manager>`"** is a warning, never a refusal (spec): any other watcher file. The host is added; both managers will report its bots. A watcher of the same NAME from another home (two owners each calling their manager `mgr`) is said as such, and since the file is named after the manager, this add takes the file over.
- **`rm` when the host is unreachable.** The ledger line goes first: that is what stops the checks. Then `--unwatch`, capped like the probe; when it fails, `rm` still exits 0 and says on stderr that the record stays and how to remove it later. A stale record can only make another manager's `add` warn, and this manager's next `add` of that host replaces it. `--no-probe` skips the call. No call at all when this home has no `host-id` (it never wrote a watcher file anywhere).
- **`--unwatch` removes only its own home's record** (the file's first word must be the caller's host-id), so a manager cannot remove the record of another home's manager of the same name.
- **A manager name the file cannot carry.** The name becomes a file name on another machine and a word of an ssh command line, so only `[A-Za-z0-9_][A-Za-z0-9._-]{0,63}` is sent. A manager bot named otherwise (a bot name may be any directory name) writes no watcher file and `add` says so; everything else works.
- **The remote words are validated on both sides.** The sender builds the command from words already matched against `mgr_re`, `hid_re` and `alias_re` (nothing in them needs quoting in any shell); the receiver matches them again before a file name is made from one. What the receiver lists comes back as untrusted as the rest of the answer: a `watcher` line counts only when its four words match.

Why text and not `ssh -G`: `ssh -G <alias>` evaluates the configuration, and a `Match exec "…"` line RUNS its command. Asking ssh about every candidate while the user types would run such commands once per alias per keystroke (spec: "never `ssh -G` during search"). So the candidates and their `user@host:port` come from the files' text; `ssh -G` runs once, for the alias the user chose (Task 8).

What the reader does, and does not:
- A line is `Keyword arguments` or `Keyword=arguments`, the keyword in any case, an argument optionally in double quotes; a `#` word ends the line. CRLF endings are fine. A file is decoded as UTF-8 with undecodable bytes replaced, never rejected.
- `Host a b *.c !d`: every pattern with no `*`, `?` or `!` that is an alias `hosts add` would take (`ALIAS`) is a candidate, once, in file order. A pattern is never a candidate.
- A candidate's `HostName`, `User`, `Port` and `ProxyJump` are the first value among the `Host` blocks whose patterns match it (ssh's first-obtained-value rule, with `*`, `?` and `!` negation), the options above the first `Host` line included, so `Host *` / `User dykim` gives every candidate its user.
- `Match`: never evaluated. Everything from a `Match` line to the next `Host` line is skipped, an `Include` in there too.
- `Include`: several paths, `~/x`, an absolute path, anything else relative to `~/.ssh`; globs expanded and sorted. An Include inside a `Host` block is read as if it stood at the top level (ssh applies it only when that block matches): its hosts are still candidates, and `ssh -G` on the chosen one shows what ssh will really do.
- Bounds, so that no configuration can hang or crash the picker: 32 files in all, 256 KiB read of each, 8 levels of Include, 2000 `Host` blocks, 500 candidates (a search over 500 x 2000 patterns takes 0.4 s, measured); a file is read once (which is also what ends a cycle of Includes); only a regular file is opened (a FIFO would block for ever); a missing or unreadable file is no file.

```python
# ---- ~/.ssh/config, read as text ---------------------------------------------
# The add-host picker lists the Host aliases of ~/.ssh/config and of the files it Includes. They are read here as text
# and never through `ssh -G`: that evaluates the configuration, and a `Match exec` line runs a command, once per alias
# asked about. `ssh -G` runs for the one alias the user chose. A configuration is the user's own file, but nothing in
# it may hang or crash the picker: a bound on the files, on the bytes read of each, on the depth of Includes, on the
# blocks and on the candidates; each file once (a cycle of Includes ends there); only a regular file is opened (a FIFO would block).
ALIAS = re.compile(r"[A-Za-z0-9._@][A-Za-z0-9._@-]{0,254}")   # what `claude-discord hosts add` takes as an ssh alias
SSH_MAX_FILES, SSH_MAX_BYTES, SSH_MAX_DEPTH, SSH_MAX_BLOCKS, SSH_MAX_HOSTS = 32, 1 << 18, 8, 2000, 500


def ssh_blocks(path: Path, home: Path, depth: int = 0, seen: set | None = None) -> list[tuple]:
    """The Host blocks of an ssh configuration file in file order, as (patterns, {option: its first value}), with the
    blocks of each Include where it stands. The options above the first Host line are a block for `*`. A Match block is
    (None, {}): never evaluated, so nothing in it counts, an Include neither."""
    seen = set() if seen is None else seen
    try:
        real = path.resolve()
        if depth > SSH_MAX_DEPTH or real in seen or len(seen) >= SSH_MAX_FILES or not real.is_file():
            return []
        seen.add(real)
        with open(real, "rb") as f:
            text = f.read(SSH_MAX_BYTES).decode("utf-8", "replace")
    except (OSError, RuntimeError):   # RuntimeError: a loop of symlinks, before Python 3.13
        return []
    cur = (["*"], {})
    blocks = [cur]
    for line in text.splitlines():
        m = re.match(r"\s*([A-Za-z]+)\s*(?:=\s*|\s+)(.*)$", line)
        if not m:
            continue
        key, words = m.group(1).lower(), []
        for quoted, bare in re.findall(r'"([^"]*)"|(\S+)', m.group(2)):
            if bare.startswith("#"):
                break
            words.append(quoted or bare)
        if key in ("host", "match"):
            cur = (words if key == "host" else None, {})
            blocks.append(cur)
        elif cur[0] is None:
            continue
        elif key == "include":
            for w in words:
                pattern = str(home / w[2:]) if w.startswith("~/") else w if w.startswith("/") else str(home / ".ssh" / w)
                for p in sorted(islice(glob.iglob(pattern), SSH_MAX_FILES)):
                    blocks += ssh_blocks(Path(p), home, depth + 1, seen)
        elif key in ("hostname", "user", "port", "proxyjump") and words:
            cur[1].setdefault(key, words[0])
    return blocks


def ssh_hosts(home: Path) -> list[dict]:
    """The picker's candidates: every Host pattern of ~/.ssh/config and its Includes that is a plain alias (no `*`, `?`
    or `!`, and one `hosts add` would take), once, in file order, with what the text says of it: `hostname`, `user`,
    `port`, `proxyjump`, each the first value among the blocks whose patterns match the alias, as ssh takes them.
    Every string is cleaned: it is drawn."""
    blocks = [b for b in ssh_blocks(home / ".ssh" / "config", home) if b[0] is not None][:SSH_MAX_BLOCKS]
    rx = lambda p: re.compile(".*".join(".".join(map(re.escape, part.split("?"))) for part in p.split("*")))
    matchers = [([rx(p) for p in pats if not p.startswith("!")], [rx(p[1:]) for p in pats if p.startswith("!")], opts) for pats, opts in blocks]
    hosts: dict = {}
    for pats, _ in blocks:
        for alias in pats:
            if alias in hosts or len(hosts) >= SSH_MAX_HOSTS or not ALIAS.fullmatch(alias):
                continue
            h = {"alias": alias}
            for yes, no, opts in matchers:
                if any(r.fullmatch(alias) for r in yes) and not any(r.fullmatch(alias) for r in no):
                    for k, v in opts.items():
                        h.setdefault(k, clean(v))
            hosts[alias] = h
    return list(hosts.values())


def ssh_target(h: dict) -> str:
    """`user@hostname:port · via <ProxyJump>` as the configuration's text gives them: the alias for no HostName, 22
    for no Port, no user and no `via` when it names none."""
    h = obj(h)
    user, jump = txt(h.get("user")), txt(h.get("proxyjump"))
    return (f"{user}@" if user else "") + (txt(h.get("hostname")) or txt(h.get("alias"))) + ":" + (txt(h.get("port")) or "22") + (f" · via {jump}" if jump else "")


def fuzzy(query: str, hosts: list[dict]) -> list[dict]:
    """The hosts a search finds, best first: an alias that starts with the query, one that holds it, one that holds its
    characters in order, then a host whose target holds it; file order within each, and for no query at all."""
    q = query.lower()

    def score(h: dict) -> int | None:
        a = h["alias"].lower()
        if a.startswith(q):
            return 0
        if q in a:
            return 1
        rest = iter(a)
        return 2 if all(c in rest for c in q) else 3 if q in ssh_target(h).lower() else None

    return [h for s, h in sorted(((score(h), h) for h in hosts), key=lambda sh: 9 if sh[0] is None else sh[0]) if s is not None]
```

A candidate the last pass already checked is marked `already checked`; the CLI is what refuses it (exit 3).

While a call runs the dialog says what it is doing, the Input is disabled (a further Enter does nothing) and `esc` still closes it; an answer that arrives after that is dropped. def run_capped(argv: list, cap: float, stdin: str | None = None) -> tuple[int, str, str]:
    """A command run to its end, or to `cap` seconds, when its whole process group is killed (a child of it that hangs
    would otherwise keep the pipes open and this call with them): (exit status, stdout, stderr). 124 for the cap, 127
    when it cannot be started. Each stream is cut at 64 KiB and cleaned of what must not be drawn; its line breaks
    stay. `stdin` is how a value travels to the command: never in its argument list."""
    try:
        p = subprocess.Popen(argv, stdin=subprocess.DEVNULL if stdin is None else subprocess.PIPE, stdout=subprocess.PIPE,
                             stderr=subprocess.PIPE, start_new_session=True)
    except OSError as e:
        return 127, "", f"cannot run {argv[0]}: {e.strerror or e}"
    try:
        out, err = p.communicate(None if stdin is None else stdin.encode(), timeout=cap)
        rc = p.returncode
    except subprocess.TimeoutExpired:
        try:
            os.killpg(p.pid, signal.SIGKILL)
        except OSError:
            pass
        out, err = p.communicate()
        rc, err = 124, err + f"\nno answer within {cap:g} s".encode()
    return (rc, *(clean(b[:65536].decode("utf-8", "replace"), UNSAFE_NL).strip() for b in (out, err)))


def ssh_effective(ssh: str, alias: str) -> list[str]:
    """`ssh -G -- <alias>`: what ssh itself will use for the ONE alias the user chose, the lines that say where a
    connection goes and through what. Never run for a candidate while searching: evaluating the configuration can run
    a `Match exec` command, which is also why it gets 5 s and no more."""
    rc, out, err = run_capped([ssh, "-G", "--", alias], 5)
    lines = [l for l in out.splitlines() if l.split(" ", 1)[0] in ("hostname", "user", "port", "proxyjump", "proxycommand")]
    return lines or [f"nothing (exit {rc}" + (f": {err.splitlines()[-1]})" if err else ")")]


class AddHost(ModalScreen):
    """`a` on the Configuration tab: a search over the Host aliases of ~/.ssh/config (ssh_hosts), or an alias typed in.
    Enter on a candidate shows the check `hosts add` runs first (the line its --dry-run prints) and what `ssh -G` says
    of that one alias; a second Enter runs `hosts add`; after a host that did not answer (exit 5) a third adds it
    unchecked. Every call runs in a worker thread, so a probe that takes its whole cap leaves the screen alive.
    Dismissed with what there is to say, or None."""
    CSS = f"""AddHost {{ align: center middle; }}
    #add {{ width: 104; max-width: 96%; height: auto; border: round {BRAND}; padding: 1 2; }}
    #cands {{ height: auto; margin: 1 0; }} #info {{ height: auto; }}"""
    BINDINGS = [Binding("escape", "cancel", "cancel"), Binding("up", "move(-1)"), Binding("down", "move(1)")]
    ROWS = 8   # candidates drawn at once

    def __init__(self, hosts: list[dict], listed: set) -> None:
        super().__init__()
        self.hosts, self.listed = hosts, listed   # the candidates of ~/.ssh/config; the aliases the last pass checked
        self.found: list[dict] = []
        self.at = 0
        self.step, self.alias = "search", ""      # search -> shown -> (running) -> failed; the alias the last Enter chose

    def compose(self) -> ComposeResult:
        with Vertical(id="add"):
            yield Static(Text.assemble(("Add a host", f"bold {BRAND}"), ("    from ~/.ssh/config and its Includes", DIM)))
            yield Input(placeholder="search, or type an ssh alias", id="q")
            yield Static("", id="cands")
            yield Static("", id="info", markup=False)

    def on_mount(self) -> None:
        self.query_one("#q", Input).focus()
        self.search("")

    def say(self, text: str, style: str = DIM) -> None:
        self.query_one("#info", Static).update(Text(text, style))

    def search(self, query: str) -> None:

        self.found = fuzzy(query, self.hosts)

What the popup is:
- **Where its content comes from.** The ledger's own line, through `hosts list --json` in a worker when the popup opens (name, kind, env KEY NAMES: the TUI never reads the ledger file and never sees a value); the target from `~/.ssh/config` as text (`ssh_target`; `ssh -G` is not run here) with the machine's own hostname from the state in parentheses; `last check` from `state.json` as the app holds it (the reach, for how long, the monitor's reason, when it was checked, and under it the monitor's recovery command), repainted every 2 s, so a pass that ends while the popup is open shows.
- **Editable:** the display name (an Input that takes no whitespace and no quote, 64 characters: what `h_word` would refuse cannot be typed), the kind (a radio pair drawn `( ) server   (●) laptop`; space or an arrow flips it while it has the focus), and the env words. **Not editable:** the alias (it is the host's key in `state.json` and on the host's watcher record: a rename is `rm` and `add`) and the target (it is ssh's configuration).
- **Env values are always masked.** A word of the line is drawn `KEY ••••` whatever it holds: the popup does not know the value. To add or change one, type `KEY` and a new value in the two fields under the list (the value field is a password field: bullets while typing) and press Enter there; to remove one, type its `KEY` and no value. That stages the change: the list says `(new)`, `(changed)` or `(removed on save)` beside the key. There is no key to show a value.
- **Unsaved changes** are said in the title (`Host · wmac    ● unsaved changes`) and beside each staged env key.
- **Save is ONE call:** `hosts set <alias> --stdin`, with every change as a line of its stdin (`name=…`, `laptop on|off`, `KEY=VALUE`, `KEY=`). One call is one rename of the ledger: a save is all there or not at all, and a monitor pass never reads half of it. A value travels on stdin only: it is in no process's argument list, in no log and in no file but the ledger. A key and value typed but not entered are saved too. On exit 0 the popup closes and the CLI's line is said; on any other exit its message stays on the popup (as text) with the changes still staged.
- **Stop monitoring this host** asks (`Confirm`, No by default), then runs `hosts rm <alias>`: the monitor keeps the host a day as "left the ledger" (it already does). Disabled for `local`, which the CLI would refuse.
- **Keys and focus.** Tab and Shift+Tab move: display name → kind → KEY → value → Save → Stop monitoring. Enter in the name or the KEY field moves on; Enter in the value field stages; Enter or space on a button presses it. `esc` closes; with unsaved changes it asks first (No by default).
- **A ledger the CLI cannot give** (it failed, or its output is not the JSON expected: another version, a broken shim) is said on the popup and leaves every field and Save disabled. Every field of the JSON is read through `txt`/`obj`/`seq`/`ids` after `clean`: a number for a name is an empty name, an object for `env` no keys, never an exception.
- **A host that left the ledger** (`left_s` in the state) has nothing to set: Enter on it still shows its raw fields (`Detail`), as before 1.12.0. So does an entry of the state that is no object.
- **`x` and `l`** on a host row are the mock's two keys: `x` asks, then `hosts rm`; `l` runs `hosts laptop <alias> on|off`, the opposite of what the last pass saw. Each is one CLI call in a worker; what the CLI says is shown when it ends.

class Kind(Static, can_focus=True):
    """The host popup's kind, a radio pair drawn `( ) server   (●) laptop`: space or an arrow flips it while it has the focus."""
    BINDINGS = [Binding("space", "flip"), Binding("left", "flip"), Binding("right", "flip")]
    laptop = False

    def paint(self) -> None:
        pair = [(f"{'(●)' if on else '( )'} {word}", "bold" if on else "") for word, on in (("server", not self.laptop), ("laptop", self.laptop))]
        self.update(Text.assemble((fit("kind", 16), DIM), pair[0], "   ", pair[1], ("    a laptop that is off is not alerted", DIM)))

    def action_flip(self) -> None:
        self.laptop = not self.laptop
        self.paint()
        self.screen.changed()


class HostEdit(ModalScreen):
    """Enter on a host row of the Configuration tab: that host's line of the ledger. What can be changed: its display
    name, its kind and its env words. The ledger is read through `hosts list --json` (key names only: this program
    never sees a value) and changed through `hosts set <alias> --stdin`: Save sends every change in that one call, a
    new value on stdin and in no argument list. A value is typed masked and is never drawn: an env word shows `••••`
    whatever it holds, and to change one is to type a new one. Dismissed with what there is to say, or None."""
    CSS = f"""HostEdit {{ align: center middle; }}
    #host {{ width: 112; max-width: 96%; height: auto; border: round {BRAND}; padding: 1 2; }}
    #host Horizontal {{ height: 1; }} #host .lab {{ width: 16; color: $text-muted; }} #host .hint {{ width: auto; padding-left: 2; color: $text-muted; }}
    #h-name {{ width: 26; }} #h-key {{ width: 22; }} #h-value {{ width: 34; }} #h-eq {{ width: 3; }}
    #h-buttons {{ margin-top: 1; }} #host Button {{ margin-right: 2; }} Kind:focus {{ background: {CURSOR}; }}"""
    BINDINGS = [Binding("escape", "close", "close")]

    def __init__(self, alias: str, target: str) -> None:
        super().__init__()
        self.alias, self.target = alias, target
        self.was: tuple | None = None   # (display name, laptop, env key names) as the ledger has them; None until it is read
        self.staged: dict = {}          # env key -> its new value ("" removes the key): sent by Save, drawn nowhere

Verified first: the monitor reads the ledger afresh at every pass (`run_pass`, `monitor/monitor.sh:751-781`, `done < "$dir/hosts"`), so a change needs no signal to take effect; without one it takes effect at the next pass, up to 5 minutes later.

Choices, each with its reason:
- **Check now asks the one monitor for a pass; it probes nothing itself.** A probe from the TUI would be a second judge of "reachable" beside the monitor's (another moment, another ControlPath), would not update what the table shows, and could not say anything about the host's bots. A pass by the monitor does all three, and keeps one writer of `state.json` and one poster to `#bot-health-check`. The popup's `last check` line repaints from the state when that pass ends (Task 9).
- **How it is asked: a marker file.** `monitor --check <bot>` creates `pass-now` in the monitor's state dir; the monitor's main loop meets it at its next tick (30 s at most), removes it, and runs a pass at once instead of waiting out its interval. Removed BEFORE the pass, so one request is one pass, however long it takes; a request made while a pass runs gets the pass after it. Requests only collapse (a file is there or not): pressing the button ten times is one pass.
- **It starts nothing.** With no monitor of that bot visible on this side (stopped by its owner, or it runs on the other side of a shared home) `--check` exits 1 saying so and leaves no marker: a monitor that starts later runs its first pass at once anyway. The TUI shows that line; the title already says `stopped by you`.
- **Nothing is posted earlier than before.** A finding is posted once it has held for its hold time, counted from when it was first seen (`since_s`), not in passes. One side effect, accepted: `health` counts runs for its `unknown_cap` (6 runs, `bin/claude-discord:967`), so each extra pass brings an `unknown` verdict five minutes closer.
- **After every change the TUI makes to the ledger** (an add, a save, a removal, a kind flip) it runs the same `monitor --check` and says the change and the monitor's answer together, e.g. `claude-discord: hosts: added lmd_dkim to …` / `claude-discord: monitor: mgr checks its hosts at its next tick (within 30 s)`. That is the answer to "when does this take effect": within a tick and a pass, not 5 minutes; and with no monitor running the second line says that nothing checks. A new host has no row until a pass has seen it, so without this the user could not even open its popup to press Check now. Not after a refused or failed change, a dry run or a closed dialog.
- **The CLI does not ask for a pass.** `claude-discord hosts add` from a shell takes effect at the next pass, as a hand edit always did; a person who wants it sooner runs `claude-discord monitor --check <bot>`. (The README says both.)

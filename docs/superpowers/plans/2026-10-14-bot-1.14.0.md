# claude-discord 1.14.0 bot token, rename and add Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A bot's token is replaced, a bot is renamed, and a bot is added, each with one command at a terminal, `claude-discord bot ... token | rename | add`, and from the TUI, which drives that command on a pseudo-terminal it holds. A bot's name here is its Discord username: a rename changes Discord first and then everything on this machine keyed by the name; a row whose two names differ says so (`≠ Discord: <name>`) and `=` aligns the name here to Discord's.
**Architecture:** One new verb in `bin/claude-discord`, beside `access` and built the same way: TTY on stdin and stdout, one `[y/N]` question after the U+2060 marker line, exit 0/1/2/3/4/5, `--host <alias>` through the same ssh path (`via_host`, extracted from `access`). The token is read by the CLI itself with the terminal's echo off, checked with `GET /users/@me` (token on curl's stdin) as the same bot, and written to `.env` by rename. The plugin's late-token login loop (1.9.4) is replaced by one that also waits after a gateway close 4004, so a running session logs in with the new token within 10 s. `rename` reuses `refresh`'s steps, made functions (`live_sessions`, `stop_sessions`, `start_fresh`, `untrusted`). `add` runs `setup` with its answers on stdin. `health --json` gains `discord_name` (re-read daily), the monitor's reducer keeps it, and the TUI draws it. The TUI gains three popups (`BotName`, `BotToken`, `BotAdd`) on a shared `Asking` mixin taken out of `AccessEdit`; the token goes from a masked field into a `bytearray`, to the pty only after the CLI's hidden prompt, and is zeroed.
**Tech Stack:** bash (3.2-compatible), jq (1.6+), curl, perl (rename(2)), Python 3 + Textual 8.2 (TUI), the suite's stubs (curl, ssh, claude, a launcher), python3's `pty` for the terminal tests.
**Spec:** `docs/superpowers/specs/2026-10-12-tui-redesign-hosts-access.md`, "1.13.0: access editing (write); the token parts below are 1.14.0", narrowed by the owner's 1.14.0 scope (below).

Base: `main` at `49cbd5c` (1.13.1). Branch: `feat/bot-1.14.0`. Every code block below is a `git diff` of a commit of a scratch tree in which this plan was carried out end to end (see "What was run while this plan was written"); apply each with `git apply` or by hand. ## Scope (decided by the owner 2026-10-14; not reopened here)

1. A bot's name is its Discord username, `[A-Za-z0-9_-]`. A TUI rename PATCHes Discord first, then changes the name here; if Discord refuses, nothing here changes. A bot whose two names differ is shown `≠ Discord: <name>` with one key that aligns the name here to Discord's (no Discord call).
2. Renaming a running bot: ask, stop, rename everything keyed by the name, restart with the handoff. This plan defines every keyed item, the order and what a failure leaves, and what peers on other machines see.
3. Token replacement: masked, the current token never read, validated with `GET /users/@me`, the same bot id required, `.env` mode 600 written atomically, reconnect without restart. Add a bot from the TUI: token, then its username is its name (a username outside the charset: rename it in the Developer Portal), choose project and mode, reuse `setup`, optionally start. Remote through `--host`, the token only on ssh's stdin.
4. Every write through the wrapper's verbs, TTY required, one `[y/N]` with the U+2060 marker, the token never echoed. The dev-manager rule: never run token, rename or add on a channel message's request.
5. TUI conventions: the palette, popups open on the safe button, `←` `→` between buttons, `y` answers directly, `[✓]`, `(●)`. English.

claude-discord bot [...] <bot> rename <new name>
claude-discord bot [...] add [--mode none|dev-manager|autoresearchclaw] [--start]
claude-discord --version --bot <hex of the project> <hex of the first word> <words>...     (what --host runs there)

## What this plan settles, and why

Decisions marked **(owner?)** are the ones an owner may reasonably overrule; each names its alternative.

1. **(owner?) A verb of its own, `bot`, not `access <bot> token|rename`.** `access` is about who may drive a bot and writes `access.json`; these write `.env`, the bot's directory and Discord. Sharing `via_host`, the marker and the exit codes keeps them one family. Alternative: `access <bot> token` / `access <bot> rename <new>` (one verb, one `--version --access`), and `add` under `setup`.
2. **The token is read by the CLI, from its terminal, with the echo off before the prompt is printed.** So it is never an argument (ps, history), never in the ssh command (`--host` runs under `ssh -t`, and the token is typed into, or written by the TUI to, that terminal), never in what the TUI reads back (the pty does not echo it). The TUI writes it only when what the CLI printed ends with `\n` + `Token (hidden): `, from a `bytearray` that `PtyRun.next` zeroes after the write; the field is emptied when the token is taken, and `Secret` disables Textual's copy and cut of a password field (which would put the token on the clipboard). A str of the token exists once, in the field's `value`, until `take()`; Python cannot promise more.
3. **The same bot:** the id in `<bot dir>/bot-id` (health keeps it since 1.9) must be the token's; with none kept, the token's username must be the bot's name, else refused. Alternative considered: refuse whenever no id is kept (safer, but a bot never checked by health could not get a token).
4. **Reconnect.** `.env` is written to `.env.cd.$$` (umask 077) and renamed over: the plugin reads `.env` by path every 10 s while it waits, so the new inode is seen (proved with bun, below). discord.js 14.25.1 treats a gateway close 4004 (a token reset) as unrecoverable: the shard emits `shardDisconnect` and is never retried, and the 1.9.4 loop only waited out a refused *login*. The new loop waits, after each login, for a `shardDisconnect` with code 4004, then marks that token bad and waits for another in `.env`; any other close is discord.js's to handle. A reset invalidates the old token, so a replaced token always comes with such a close. A session started before 1.14.0 has the old loop: the CLI says `refresh <bot> --force` (it cannot tell which loop a running session has).
5. **Rename order.** Checks first (a name, not taken, not reserved, no peer of that name in `peers.json`, a manager name free of a backend, the token in `.env` being this bot's, `claude agents --json` answering, a trusted workspace when it runs), then the plan printed, then the question, then: (a) `PATCH /users/@me` unless Discord has the name already (refused: exit 1, nothing here changed); (b) `discord-name` written; (c) the sessions stopped (one that will not die: exit 1, nothing renamed here, "Discord calls it X now: run this again"); (d) a manager's keeper and monitor stopped and a `stopped` marker made under the new name (so no hook starts a backend for it meanwhile); (e) the directory renamed with perl's rename(2) (fails: `b_undo` starts again what was stopped); (f) `access.log`; (g) every `peers.json` of this machine's projects, by the bot's id; (h) the scratch directory; (i) a manager's `records/monitor/<old>` moved, `state.json .manager` rewritten, the backend started unless its owner had stopped it, its watcher record on each ledger host re-recorded (`--watch new`, then `--unwatch old`); (j) the session started under the new name from its handoff (`start_fresh`, which puts the handoff back if the start fails). After (e) each failure is said with the command that finishes it, exit 1; the name here is the new one either way.
6. **(owner?) A session cannot rename its own bot** (`DISCORD_STATE_DIR` is the bot's directory: exit 2). The rename stops that session on the way, which would kill the rename. DY-DevBot is renamed from a terminal or from the TUI (a process of its own, which follows the manager's records to the new name: `retarget`). Alternative: a detached helper (`setsid nohup`) that waits for the session to stop and then renames; more moving parts, and its failures would be said to nobody.
7. **(owner?) Peers on other machines are not changed.** A peer's hooks match a peer by `bot_id`; the old name in their `peers.json` is only a label. The CLI says so and names the command for their owner. Alternative: ssh to each ledger host and rewrite `peers.json` there (needs a new remote verb, and a peer's machine is often not on this manager's ledger).
8. **`=` is `rename` to Discord's name.** When Discord's username is already the new name, no PATCH is sent; everything else is the same transaction. The TUI opens the name popup preset and runs at once, so the CLI's one question is still asked.
9. **(owner?) `add` takes the project's channel and owner from `config.env`** (a project with a bot already), mention required, and the mode; `--start` runs `--bg --name`. It refuses a project with no `config.env`, a token whose bot is set up in any recorded project already (two sessions on one token both answer), and a username that is no name here ("Rename it in the Developer Portal first"). It drives the real `setup` with its answers on stdin and `CLAUDE_DISCORD_SETUP_NOASK=1` (no install questions); a failed setup removes the directory it made. Alternative: `add` asks for a channel and the allowed users too (a second form in the popup).
10. **(owner?) `health` re-reads the username once a day** per bot (one more `users/@me` per bot per day; a failed read keeps the name and retries in an hour). `discord_name` is `null` from a host before 1.14.0, and the TUI then shows nothing. Alternative: read it only when `bot-id` is missing (the name would go stale after a rename in the Developer Portal).
11. **Stopped versus running:** a stopped bot is only renamed (`claude-discord --bg --name <new>` starts it, said); a running one is stopped and started again; the trust check runs only when it runs.
12. **One backend per manager name per machine:** a manager may not take a name that has `records/monitor/<name>` or a ledger in another recorded project (`b_mgr_free`), also for `add --mode dev-manager`.
13. **`--host`:** `via_host bot 1.14.0 ...` asks the host's `--version` first (as `access` does); older or no answer is exit 5, and nothing else is sent. The host's `--version --bot <hex project> <hex first word> <words>` is decoded into `bot --project <dir> -- <word> <words>`; names and paths travel as hex, the new name is checked against `b_name_re` here before it is sent.
14. **The TUI's key `a` on the Bots tab** adds a bot (it was unbound there); on the Configuration tab it adds a host as before. The foot at 110+ columns reads `↑↓ select  space expand  enter all fields  e access  a add bot  c copy fix  ←→ tabs  q quit`; narrower, `↑↓ move  space open  e edit  a add  c copy  ←→ tabs  q quit` (`enter all` moved under an opened row's `keys` line, measured 74 cells at 80 columns). `n`, `t` and `=` are listed on that `keys` line and on the `≠ Discord` line.
15. **Version 1.14.0, one release.** The CLI, the patch and the TUI need each other only through the CLI's text; `--version` decides what a remote host is asked.

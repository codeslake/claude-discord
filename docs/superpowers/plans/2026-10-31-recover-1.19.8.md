# 1.19.8: recover respawns a settled bot, says why it refused, and the monitor says when it cannot recover

Incident 2026-10-30 (thread 1565537446878519449): the 2.1.314 upgrade restarted the daemon, which adopted 9 jobs and
3 s later settled 5 bots `done`. The monitor's `bot <bot> recover --yes` exited 1 for all four it tried, with nothing
in recover.log: the monitor ran with a bare PATH (no `claude`, fixed in dotfiles 6154ba9), and recover refuses before
it logs. Had `claude` been found, recover reads `claude agents --json` (no --all), misses the settled pinned job, and
starts a FRESH session: the conversation is lost. `claude respawn <id>` by hand brought all four back with it.

## Changes

1. **A settled pinned job is respawned** (`bin/lib/bot.sh`, recover). Only when the no---all listing has no last
   session (`b_last` empty) and `pinned-job` holds an id: `claude agents --json --all`, the ONE row whose `id` equals
   it, `cwd == $(pwd -P)`, `state == "done"`. That row is the last session (`how: pinned-job (done)`), so the act is a
   respawn (one row) and the conversation is kept. Nothing else widens: plugin-sessions and live_sessions stay on the
   no---all listing ("a retired session is not listed": only the pinned id is looked up). A failed --all listing is
   the old behaviour (a fresh start), not a refusal.
2. **`--yes` never brings back a bot a person stopped** (1.19.7 `person_stopped`): recover --yes (the monitor, boot)
   refuses, logged, exit 1, nothing run. Without --yes the person is asked, as before. (health holds such a bot before
   the monitor decides; this is the second guard, pinned by a test.)
3. **Every refusal is in recover.log**: `b_rlog` is defined before the first refusal; the failed listing (b_unknown),
   the untrusted workspace, two listed sessions, a foreground session, a moving transcript under --fresh, and (2)
   each write `<time> <user> <host> recover[ --yes]: refused: <reason> (exit 1)`. The monitor's "[recover failed] ...
   its recover.log on that host says why" is then true.
4. **The monitor says when it cannot recover** (`monitor/monitor.sh`): at start, `command -v claude` failing logs one
   `warning: claude is not on PATH (<PATH>): the automatic recover cannot run` line in monitor.log.

## Tests (test-install.sh only; core untouched)

- (a) a pinned job listed only by --all, state done, this cwd: the plan says `pinned-job (done)` and `run: claude
  respawn <id>`; after y, the stub logged `respawn <id>`, recover.log has it. Mutant: drop the --all lookup -> a fresh
  start, FAIL.
- (b) --all row of the pin but another cwd, or state not done, or a done row that is not the pin: a fresh start as
  before.
- (c) recover --yes with daemon.log's last line for the pin `bg settled <pin> (killed)` (no shutdown/start in 60 s, no
  newer marker, no own-stop line): exit 1, `refused: stopped by a person` in recover.log, nothing in claude.calls; the
  same without --yes reaches the question. Mutant: drop the guard -> respawned, FAIL.
- (d) `claude agents` failing: exit 1 and a `refused:` recover.log line. Mutant: log after the refusal -> FAIL.
- (e) the monitor started with a PATH that has no claude: the warning line in monitor.log; with claude: none.
- Both suite files, timing against main on lmd79 (install must stay within main + 1 s).

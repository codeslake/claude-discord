# claude-discord 1.16.0 Implementation Plan: the recovery keys `f` (one bot) and `F` (several)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tests first: each behaviour change begins with a test that fails on `main` (`3e173a3`) and passes after the change; say in the commit which assertion it is. One task at a time, no parallel work.

**Goal:** A problem row of the TUI's Bots tab is recovered with one key: `f` recovers the selected bot, `F` every bot that can be recovered, each after one question, and a batch runs to its end and lists what failed. For a `down` bot the recovery is `claude respawn <id>` when the bot's last session is still listed by `claude agents`, else `claude-discord --bg --name <bot>` (the spec's "Next after 1.13.0"). Nothing is run without a `y`; nothing is run on a bot the TUI cannot reach; two sessions never end up on one token.

**Architecture:** One new act of the existing `bot` verb, `claude-discord bot [--host <alias> --manager <bot> --project <dir>] <bot> recover [--fresh]`, decides on the bot's own machine what to run (it is the only place that can read `claude agents --json`, `<bot dir>/pinned-job` and `<bot dir>/plugin-sessions/`), prints the command, asks its one `[y/N]` after the U+2060 marker line, runs it, and exits with that command's status. The TUI drives it on the pty it already holds for `bot ... token|rename|add` (`PtyRun`, `Asking`, `BotPopup`, `AccessAsk`): `f` opens a popup that runs at once (as `=` does) and asks the CLI's question in `AccessAsk`; `F` opens one popup that lists the rows, asks once, then runs the verb for each row in turn on the pty, answering each CLI question `y` itself, and lists the results. The monitor's alert text and `health --json` do not change; the row changes at the monitor's next pass, which the TUI asks for (`wrote()` -> `monitor --check`).

**Tech Stack:** as 1.15.0: bash 3.2-compatible (the act lives in `bin/lib/bot.sh`, sourced on demand with `sessions.sh` and `remote.sh`), jq 1.6, the suite's stubs (`claude`, the launcher, the pty driver `drive.py`), Python 3 + Textual 8.2 (the TUI), the pilot's `fake_pty` and `FakeRun`.

**Spec:** `docs/superpowers/specs/2026-10-12-tui-redesign-hosts-access.md`, "Next after 1.13.0": "Recovery fix keys: `f` (one bot) and `F` (several): show the commands, ask once, run; a batch runs to the end and lists failures. `down` prefers `claude respawn <id>` when the bot's last session (plugin-sessions) is still in `claude agents`, else `--bg --name`." And 1.10.3 option A: every bot session revives a dead keeper unless it was stopped by you.

Base: `main` at `3e173a3` (1.15.0). Branch: `feat/recover-1.16.0`.

## Scope / decisions (what this plan proposes; each marked **owner decision** is for the owner)

1. **(owner decision 1) The decision respawn-vs-start is made by the wrapper on the bot's machine, as a new act of `bot`: `claude-discord bot <bot> recover [--fresh]`.** The TUI never builds or runs the monitor's fix line itself. Why: the fix line (monitor/monitor.sh:558-570) is shell text for a person to paste (`cd ~/rcps && claude-discord --bg --name photobot`, or `ssh <alias> '...'`), not an argv; and only the bot's host can read `claude agents --json`, `pinned-job` and `plugin-sessions/`. `bot` already has everything the act needs: `--host` through `via_host` (bin/lib/remote.sh:106-181, `ssh -t` at a terminal), the `--version --bot <hex> <hex> ...` transport (bin/claude-discord:418-423, no new form), the marker + one `[y/N]` (`b_ask`, bin/lib/bot.sh:119-124), the exit codes 0/1/2/3/4/5, `live_sessions`/`stop_sessions`/`start_fresh` (bin/lib/sessions.sh), `untrusted` (bin/claude-discord:377-380), the self-session guard (bin/lib/bot.sh:300-301), the dispatcher's `bot) libs="sessions remote bot"` (bin/claude-discord:466). Alternative: a top-level verb `claude-discord recover <bot>` (a new lib, a new `--version --recover` form, a new `via_host` caller, a new TUI argv builder; nothing gained). Alternative 2: the TUI runs the fix line with `bash -c` / `ssh <alias> '...'` (no session knowledge, no question of the CLI's, no exit-code family).
2. **(owner decision 2) Which verdicts `f`/`F` take, and what each runs.** `down` -> `recover`: respawn when the bot's last session is still listed, else `--bg --name`. `stale` -> `recover --fresh`: what the fix line says today (`refresh <bot> --force`, monitor.sh:560): every listed session stopped (`stop_sessions`), then `--bg --name` (the conversation is lost; a wedged session wrote no handoff). Every other verdict is refused by the TUI with its fix text in a notification: `duplicate` (the fix is to choose by hand which copy to stop, monitor.sh:561), `unreachable` (the token, :562), `nostate` (:563), `throttled`/`apierror`/`blind`/`patchfail`/`hostdown` (a re-check, an update, an ssh probe: not a recovery), `unknown` (no token), and a row of a host the last pass could not reach (`cut_off`, tui/claude_discord_tui.py:206-209: the fix line is already hidden there, :339-342). Alternative: respawn for `stale` too (keeps the conversation and restarts the worker); not proposed because the one no-hooks worker ever seen was a respawned one (README.md:1598, Claude Code 2.1.280 -> 281), and a `stale` bot whose worker runs no hooks would be respawned into the same state again by the next `f`.
3. **(owner decision 3) `F`'s "ask once": one popup of the TUI listing the rows, one `y`; the CLI's own `Recover <bot>? [y/N]` is still printed by each run and answered `y` by the TUI without a second popup.** No `--yes` flag on the verb: 1.13.0 refused a skip flag for `access`, and a person at a terminal is always asked. The popup lists, per row: the bot, its host (display name), the verdict with how long it stood, and what will be asked of the host (`respawn if its last session is listed, else --bg --name` for down; `stop every session, then --bg --name` for stale). Alternative: `recover --yes` (a simpler TUI; a flag that skips the question).
4. **(owner decision 4) After a run the row is not changed optimistically; the TUI asks the monitor for one pass (`wrote()` -> `ask_pass()` -> `monitor --check`, tui:2645-2663), and the verb does not wait for the plugin server to come up.** The verdict comes from Discord (health), not from the exit status of `claude respawn` or the launcher; a respawned worker may come up mute (memory: a fleet claim revives a job with no prompt; a respawned worker ran no hooks once), and only the next pass can tell. The popup's result line says what ran and its exit status; the row says `down` until the pass. Alternative: the verb waits up to 20 s for exactly one plugin server; `count_servers` is an inner function of the `health` block (bin/lib/health.sh:193-230) and would have to move to the top or to `sessions.sh`.
5. **(owner decision 5) The monitor's fix lines and the alert text stay as they are** (`--bg --name` for down, `refresh --force` for stale). Switching the posted fix line to `claude-discord bot <bot> recover` would make the alert's command fail with `bot`'s usage on every host still at 1.15.0 (the fix line runs on the bot's host over ssh, :557). Proposed for the release after, once every host is 1.16.0. The TUI's fix line keeps the command (`c` copies it) and gains the key hints.
6. **(owner decision 6) Budget and a probe.** (a) The suite's new cases are estimated at +0.45 s here, +0.9 s on lmd42 (36.6 -> ~37.5 s, under the 38.5 s trigger, under 40 s): the "not slower than `main`" sentence is read as 1.14.0's (no more than 1.5 s above `main` in the same hour), since a feature with tests cannot be literally not slower. ## Names this plan adds

**CLI:**

```
claude-discord bot [--host <alias> [--manager <bot>]] [--project <dir>] <bot> recover [--fresh]
```

**Exit status** (the family of `bot`): 0 it ran and the command exited 0; 1 it could not (no such bot, `claude agents --json` failed or is no list, two or more sessions listed without `--fresh`, an untrusted workspace when a start would follow, a session that would not stop under `--fresh`, or the command it ran exited non-zero: said with the command and its status); 2 usage, or a session recovering its own bot; 3 no terminal: the plan printed, nothing run; 4 answered no; 5 `--host`: no answer, or the host is older than 1.16.0.

**What it prints** (local, `down`, the last session listed; `⁠` is the U+2060 marker line):

```
claude-discord: bot: recover alpha on lmd79, /home/u/p/.claude/discord-agents/alpha
    its last session a8305585 (pinned-job) is listed by claude agents (background, state done, pid 2533799)
    run: claude respawn a8305585    (the session is restarted with the flags it was started with; its conversation is kept)
⁠
Recover alpha? [y/N] y
claude-discord: bot: ran claude respawn a8305585 (exit 0); the monitor's next pass says whether alpha answers
```

The last session not listed:

```
claude-discord: bot: recover alpha on lmd79, /home/u/p/.claude/discord-agents/alpha
    its last session a8305585 (pinned-job) is not listed by claude agents, and no session of alpha started in /home/u/p is
    run: cd /home/u/p && claude-discord --bg --name alpha    (a fresh session; handoff.md is folded in when there is one)
⁠
Recover alpha? [y/N] y
claude-discord: starting alpha
...the launcher's lines...
claude-discord: bot: ran claude-discord --bg --name alpha (exit 0); the monitor's next pass says whether alpha answers
```

`--fresh` (stale): the listed sessions named, `run: claude stop <id> (each), then claude-discord --bg --name alpha`; after `y`, `stop_sessions`' lines, then the start. Two or more sessions listed without `--fresh`: `claude-discord: bot: 2 sessions of alpha are listed (accl1111 pid 4242, acc22222 pid 4243): two on one token both answer. Stop the copy by hand (claude stop <id>), or recover --fresh stops every one and starts one; nothing was run` (exit 1, before the question).

**How "the bot's last session" is found** (`b_last_job`): (1) `<bot dir>/pinned-job` (hooks/turn/on-session-start:89-121: the 8-hex job id of the last background session this bot pinned, written at every startup and resume) when it is listed by `claude agents --json` (no `--all`: retired sessions are not listed) with `.cwd == $(pwd -P)`; (2) else the newest file of `<bot dir>/plugin-sessions/` (hooks/lib/discord.sh:153-184: one marker per session, named by the full session id, touched on every hook event) whose name equals a listed row's `.sessionId`, or whose first 8 characters equal a row's `.id` (a resumed job keeps its id and changes its sessionId, bin/claude-discord:717-725); (3) else `live_sessions "$bot" "$d"` (by name, or by the job record's `DISCORD_STATE_DIR`, with `.cwd == $(pwd -P)`): one row -> that; none -> a start; two or more -> refused. ## What this plan settles, and why

- **Today's fix command is built once, in the monitor's reducer** (`def fix`, monitor/monitor.sh:558-570), stored per entry by `observe` (`. + {fix: fix}`, :606) in `state.json` (`bots.<host|project|bot>.fix`, hosts too), posted in the alert text (`finding_text`, :576-579, `group_payload`, :594-596: `fix:`/`복구:`), and drawn by the TUI only for a problem row (`fix_of`, tui:339-342: `rank == 0`, i.e. `PROBLEM = down, stale, duplicate, unreachable`, :65, and not `cut_off`) as the full-width line `fix  <command>   c copies it` (:404-405) that `c` copies (`action_copy`, :2621-2625). `health --json` has no `fix` field (bin/lib/health.sh:713-722: `bot verdict detail servers turn_min oldest_unanswered last_seen unanswered_min refresh_tail trusted owner_id channel channel_name last_message_at mode discord_name access`). Local vs remote: `cd <project, ~-shortened, quoted when odd> && claude-discord <verb>` vs `ssh <alias> 'cd ... && ~/.local/bin/claude-discord <verb>'` (`cdp`, `cd`, `wrap`, :551-557). Runnable commands: `down` (`--bg --name`), `stale` (`refresh --force`), `throttled|apierror` and a project's `blind` (`health`), `patchfail` (`update`), `hostdown` (`ssh ... 'echo up'`), a host's `blind` (`--version`); text only: `duplicate`, `unreachable`, `nostate`. So "show the commands" in the TUI is already done for the four problem verdicts; this release makes two of them runnable (decision 2) and leaves the text as it is.
- **`claude respawn <id>` vs `claude-discord --bg --name <bot>`.** `claude respawn <id>|--all`: "Restart a background session (or all of them) so it picks up the current Claude binary" (`claude respawn --help`, 2026-10-15). The daemon restarts the worker from the job's `respawnFlags`, which carry the wrapper's whole launch (`--settings` with `DISCORD_STATE_DIR`, `-n <bot>`, `--append-system-prompt` with the handoff of THAT launch, `--model` as it was; bin/claude-discord:697-702, 776-783; memory: bg-resume-keeps-saved-options-and-model, fleet-claim-revives-job-without-prompt: `src=resume` sees the env, nothing is stripped). So a respawn keeps the conversation, the job id and the pin, and brings the plugin server back (the one thing `down` means: `servers = 0`, bin/lib/health.sh:672-673, counted from `bun ... start` processes whose environ carries the bot's `DISCORD_STATE_DIR`, :193-230); it re-reads no settings (a model or flag change needs a fresh session, as the memory says), and it is the daemon's path, not `claude --bg --resume` (which, given any flag, starts a COPY under a new id: the duplicate the memory warns of; `recover` never uses `--resume`). `--bg --name` is a fresh session through the wrapper's launch (handoff folded in and moved aside, `prune_dead_sessions`, the trust gate of `claude --bg`). The spec's preference is the gentle one first.
- **"The bot's last session (plugin-sessions)"** is read as decided above: `pinned-job` first because it holds the very id `claude respawn` takes and is written at every startup and resume of a background session; the `plugin-sessions/` markers second (the spec's words; one per session, by session id, kept fresh by every hook event and pruned after 30 days without one); `live_sessions` third (today's `refresh`/`rename` lookup, which also finds a session renamed with `/rename` through its job record). Each must be LISTED (`claude agents --json`, no `--all`) and started in this project (`.cwd == $(pwd -P)`, as `live_sessions` requires): a pinned job of another cwd is a bot moved since, and respawning it would restart it there.
- **`--fresh` is `refresh --force` without the detached child.** `refresh` forks a `setsid` child because the session that runs it is the one stopped (bin/lib/refresh.sh:57-71); `recover` is run by the TUI or a person at a terminal, never by the bot's own session (the guard at bin/lib/bot.sh:300-301 applies: `DISCORD_STATE_DIR -ef $d` is exit 2), so it stops and starts in the foreground, its output on the pty the TUI reads. It reuses `stop_sessions` (a stop that fails: exit 1, nothing started, the stopped ones named, sessions.sh:15-49) and `start_fresh` (a start that fails puts the handoff back, :57-67).
- **What `f` must refuse** (safety): a verdict with no runnable recovery and a cut-off host (the TUI, `recoverable`); a session recovering its own bot (the CLI, exit 2); an unknown listing (`claude agents --json` failed or is no array: exit 1, "what runs is unknown"); two or more listed sessions without `--fresh` (exit 1, named); an untrusted workspace when a start would follow (exit 1 before the question; a respawn needs no trust check of ours: decision 6b asks whether the daemon has one); a stop that fails under `--fresh` (exit 1, nothing started). The dev-manager rule: `recover` is never run on a channel message's request (rules/dev-manager.md:47).
- **The keeper** is not touched by any of this: a bot start's `on-prompt`/`on-session-start` hooks revive a dead keeper through `ensure_keeper` only when `keeper_alive` says none runs AND no `stopped` marker stands (hooks/lib/discord.sh:227-244, `keeper_alive` :251-253); `monitor --check` after the batch is refused on the marker (monitor.sh:163, shown by `ask_pass`). 1.10.3 option A holds as it is.

## Open risks (not settled by this plan)

1. **`claude respawn` is unverified** beyond its `--help` line: whether it keeps the job id and the pin, whether the daemon checks workspace trust on that path, what it exits for an unknown id or a row the daemon considers retired, and whether a respawned worker runs hooks (README.md:1598: the one worker seen running no hooks was a respawned one, Claude Code 2.1.280 -> 281). Task 0 answers the first three; the fourth is Claude Code's.
2. **A mute revival**: a respawned worker can sit with no prompt delivered (memory: fleet-claim-revives-job-without-prompt, idle clock reset, retired at 60 m); the pin should hold it, and the monitor's next pass is the only check (decision 4). An `f` that "succeeded" (exit 0) may leave the row `down` until the pass; the popup says so.
3. **A batch over ssh is serial and each run has A_CAP 40 s to its question**: N remote hosts with a slow ProxyCommand take N × (8 s connect + the host's `--version` round trip + the run); a host that asks for a code (`HostSays`) blocks the batch until Cancel or the code. Acceptable for a handful of bots; a batch across many hosts is the owner's call at the popup (the count is in `Run N`).
4. **Textual's `F` key**: `Binding("Q", ...)` already works for shift+q (tui:2447), so `F` is expected to; the pilot presses `"F"` to prove it, but a terminal that reports shift+f differently (some Windows terminals) would not reach it. The fix line's hint names both keys either way.
5. **The budget sentence** reads "not slower than `main`"; this release can only be within +1.5 s (decision 6a). If the owner keeps the literal reading, the new suite cases must displace equal time elsewhere (candidates: the rename block's second `sleep 300` sessions, the bot block's `--host` ssh stubs), which this plan does not do.
6. **`stale` with `--fresh` loses the conversation** (no handoff from a wedged session); the alternative (respawn first) was declined for the no-hooks reason in decision 2. The owner may prefer respawn-first for `stale` with `--fresh` as a second `f` when the pass still says stale; the CLI supports both today (the TUI's mapping is one line).
7. **`pinned-job` can be stale or absent**: a foreground bot has none, a start whose pin write met the lock skipped it (on-session-start:100-104), a pre-1.9 bot never wrote one; the fallbacks (markers, `live_sessions`) cover these, and a pinned id of a RETIRED job is simply "not listed" (a start follows), which is right.

# claude-discord 1.15.0 Implementation Plan: bin/claude-discord split into a top and `bin/lib/*.sh` sourced on demand

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Tests first: each behaviour change begins with a test that fails on `main` (`6b285e5`) and passes after the change; say in the commit which assertion it is. The move itself is one commit whose message lists every added line.

**Goal:** Each call of `bin/claude-discord` parses only what it needs. Today bash parses the one 3829-line file up to the verb's `exit` (section 0 below): `monitor`, `tui`, `bot` and a launch pay 5.6-6 ms a call where 1.5-3.3 ms would do, and the suite makes ~400 such calls. After this release the file is a 775-line top (header, `monitor`, the shared functions, the `--version` forms, a dispatcher, the launch) and ten `bin/lib/*.sh` files, each sourced only by the verbs that need it. Argv and output do not change; one message does (the `setup` usage line, decided below). No feature.
**Architecture:** A move, not a refactor: every original line lands in exactly one file, unchanged (verified with `comm` on sorted line multisets); the only added lines are the dispatcher, the `[ -r ]` guards with their message, the libs' one-line header comments and the explicit `setup` usage test. ONE dispatcher, top-level code, after the `--version --access|--bot` rewrite and before the launch. Libs: no shebang, mode 644, not scripts.
**Tech Stack:** as 1.14.1: bash 3.2-compatible (`.` with `set -euo pipefail`, `$0` = the wrapper inside a sourced file, verified on the Mac's 3.2.57), jq 1.6+, the suite's stubs. Nothing new for `bash4_lint`.
**Design note:** `~/.claude/jobs/199eeafe/tmp/split-design.md` (read-only study of `main` at 6b285e5: the per-verb parse cost, the dependency table, layouts A and C2 built and measured, the 35-invocation smoke comparison, bash 3.2 checks). Its sections 0-3 are reproduced below so the plan stands alone.
**Spec:** `docs/superpowers/specs/2026-10-12-tui-redesign-hosts-access.md` (status section: 1.15.0 is this split; the recovery keys `f`/`F` move to the release after).

Base: `main` at `6b285e5` (1.14.1). Branch: `feat/split-1.15.0`.

## What this plan settles, and why

- **Today's cost is per verb, not 5.7 ms flat** (section 0): bash parses one top-level command at a time and a verb block ends in `exit`, so `setup` (82 suite calls) already stops at line 981 and cannot get faster; the money is in the verbs at the END of the file that need almost nothing (`monitor` 38 calls at 6.05 ms with no function needed, `tui`, `bot`, the launch, `--version`).
- **Layout C2, not A.** A ("the top keeps every function, only verb bodies move") still parses 1562 lines on every call and yields half of C2's saving (section 3). C2's top carries only what `monitor`, `--version` and the launch need.
- **One dispatcher, top-level.** Section 8 of the design note: a `.` inside a helper function sees the function's own `$1`. A `for` over `$libs` is a builtin loop, no fork; `case`, `[ -r ]` and `.` are builtins too. Forks added by this release: none.
- **The `[ -r ]` guard with its own message** names the cause when someone copies the one file: on bash 3.2 a missing `.` target exits 1 with a message that names no cause. `--version` and its ssh forms (`--host-id`, `--watch`, `--unwatch`) still work from such a copy: they need no lib, which is what `hosts add` relies on when it asks another machine.
- **The `setup` usage line** (decision 3): `[ -n "${2:-}" ] || { echo "usage: ..." >&2; exit 2; }` then `name=$2`. Exit 2 is what every other usage refusal of the wrapper exits (`update`, `bot`, `hosts`, `access`). The suite pins the text and that no `: line` prefix appears.
- **`monitor` first in the top**: it `exec`s `monitor/monitor.sh` and reads only `$helpers`, `$self_root`, `$self_path`; hoisted above the shared functions it parses 161 lines (1.54 ms, from 6.05). The hooks' `ensure_keeper` (hooks/lib/discord.sh:244) and the keeper itself call it unattended, so it must never depend on a lib.
- **The path shapes (addition A).** `self_root` is the physical directory of the file bash runs, resolved by `cd "${self_path%/*}/.." && cd -P .` (bin/claude-discord:126-131) whatever `$0` was: a directory symlink (`<project>/.claude/skills/claude-discord` -> `~/.claude-discord/source`, lmd42's shape, where the FILE is no symlink so `readlink -f` is skipped), the shim's `exec` through that path, a relative `$0`, another cwd. `bin/lib/` is `$self_root/bin/lib`. The suite runs one lib-needing verb (`bot`, its usage) through each shape and compares with the direct call.
- **The update window (addition B).** `update` (bin/claude-discord:2081-2123) does `git pull --ff-only` per recorded clone; git writes the worktree in index order, so `bin/claude-discord` lands BEFORE `bin/lib/*.sh` (verified with strace on a two-commit test repo: `bin/claude-discord` then `bin/lib/x.sh`); the window is the write-out of one git process (milliseconds), during which the new top finds no lib and refuses (exit 1, the message on stderr). Who calls the wrapper unattended, and what a refusal does there:
  - `hooks/turn/on-session-start:62-64`: `"$plugin_root/bin/claude-discord" patch --compat` at a startup or resume. A failure is one line in the bot's `health.log` (`on-session-start: patch failed: <message>`) and the start continues: the `if` only logs. Nothing reads that line back (`health` writes health.log at bin/claude-discord:1740 and reads it nowhere). Same as any patch failure today.
  - `hooks/lib/discord.sh:231,244` (`ensure_keeper`): `monitor --keep <bot> --detach`. `monitor` is in the top: no lib.
  - `monitor/monitor.sh:501` (local) and `:798` (over ssh): `~/.local/bin/claude-discord health --all --json --patch` once a pass. A local exit 1 with an empty document is the verdict `blind` (monitor.sh:622-623: `$doc == null or $r.rc != 0`), detail "local answered without a health document (exit 1)" (:636). `blind` holds 300 s before it is posted (`hold` at monitor.sh:546-547) and the next pass (60 s) finds the libs and the verdict returns to `ok`, so the channel is never told; the transition is one `monitor.log` line and one pass of the TUI's Hosts tab. The same as a health run that fails for any other reason today; there is no "transient" status to return instead (local 255 and 124 are `blind` too).
  - `monitor/monitor.sh:112` (`a_keeper`), the keeper's own rounds: `monitor --ensure`, in the top.
  - the TUI: `hosts`, `bot`, `access` through `--claude-discord`, all on a key press, the output shown in the popup; `monitor --check`/`--ensure`, in the top.
  - `update` itself runs the pulled tree's `patch`/`compat` (bin/claude-discord:2109-2113) after the pull returned: the libs are there.
  So no exit status or wording is changed for this: every unattended caller already tolerates a failed run as transient or logs it, and the window is one process's file writes. Documented here and in the final report; no test.
- **`compat`** stays in `bin/lib/install.sh` right after `remove_old_install` (line 534), as today.
- **Functions two verbs share**: `untrusted` (health, refresh, bot), `ledger_write` (setup via write_hosts, hosts), `record_project` (setup, health), `takes_value` (launch, refresh), `ask` (setup, tui) stay in the top; live_sessions/stop_sessions/start_fresh -> sessions.sh (refresh, bot); h_manager/h_ssh/via_host -> remote.sh (hosts, access, bot); sync_runtime/sync_compat/patch_official -> patch.sh (install, setup, compat, patch, health, launch).
- **`setup` and `install` get 0.4-0.5 ms slower** (they parse patch.sh + install.sh = 759 lines where today they stop at 981, and the C2 top carries takes_value, host_id and the --version block they do not use): 82 x 0.37 = 30 ms here. The design's open question 2 (dispatch them earlier) was declined: one dispatcher, one place to read.
- **Rollback and mixed versions**: only files move; argv and output are unchanged. A 1.14.x manager calling a 1.15.0 host over ssh runs the shim -> bin/claude-discord -> libs beside it; a 1.15.0 manager calling a 1.14.x host sees the single file. A `git pull`/`checkout` moves `bin/lib` with `bin/claude-discord`; only a hand copy of the one file breaks, and says so.

## Changed from the design note while implementing (2026-10-15)

- **`b_read`'s `local st` (main:3091) is dropped**, not moved: the suite's Ctrl-C-at-the-token-prompt case failed with `bin/lib/bot.sh: line 1: st: unbound variable` and the echo left off. A `local` is gone by the time an EXIT trap runs after an `exit` from a file sourced at top level, on bash 5.1 and the Mac's 3.2 alike (reproduced minimally in-file vs sourced: in-file sees it, sourced does not; a plain variable survives either way; subshell functions such as `select_one` and `sync_compat` keep theirs). `st` is a plain variable of the block now, as `select_one`'s `saved` is. So two of main's lines change, not one. The design note's semantics section 8 missed this shape (a trap that outlives its function's scope).
- **The suite edits a wrapper file in one place** (test-claude-discord.sh:5897, the update case's `sed` of the `patch` verb line in the stand-in repo): it now edits `bin/lib/patch.sh`. The design's suite-impact list missed it.
- **A suite race, exposed by the faster `tui` call**: the keeper's `--stop` case read the monitor's pid from `state.json` right after `tui` returned; the monitor the keeper starts writes it asynchronously.

## Task 3: the state move with its transition (1.17.1; tests first)

### 3.1 The key

`proj_key <absolute physical path>`: `LC_ALL=C` and `${p//[^A-Za-z0-9]/-}` (a bash expansion, no fork; bash 3.2 has `${x//pat/rep}` with a bracket pattern; in the C locale a range is ASCII only, as `c_match` relies on, `bin/claude-discord:142`). Equal to Claude Code's `~/.claude/projects` folder for every ASCII path (measured above: 26 + 12 of 26 + 12). **Known differences, not handled (risk 6):** a non-ASCII path (Claude Code replaces each UTF-16 unit, bash in C each byte: one Hangul syllable is `-` there, `---` here) and a path over 200 characters (Claude Code truncates and appends a hash). Neither breaks anything: the key only has to be stable and `project` is the authority; it only stops matching the transcript folder's name.

Tests (Task 3 (a)): a table from this machine: `/home/d.kim4` -> `-home-d-kim4`; `/home/d.kim4/projects/my_dotfiles` -> `-home-d-kim4-projects-my-dotfiles`; `/home/d.kim4/projects/hoi_trigger_codebase/.claude/worktrees/hoi-v2-pr` -> `-home-d-kim4-projects-hoi-trigger-codebase--claude-worktrees-hoi-v2-pr`; `/home/d.kim4/projects/RobustAlwaysOn` -> itself with dashes; `/tmp` -> `-tmp`; `/a b/c.d` -> `-a-b-c-d`; and the collision pair `/x/a_b`, `/x/a.b` -> one key.

### 3.3 The hooks: `proj_state` and `project_dir`, both shapes

In `discord.sh`, replacing `bot_project` (:57), computed once, no fork:

```bash
# proj_state: the project's state dir (config.env, peers.json, checkin/); project_dir: the project.
#   ~/.claude-discord/projects/<key>/bots/<bot>          (1.17.1 on): proj_state is up to /bots/, project_dir its `project` file
#   <project>/.claude/discord-agents/<bot>, a symlink    (a job whose respawnFlags froze the old path): the link's target, as above
#   <project>/.claude/discord-agents/<bot>, a directory  (not moved yet): proj_state is its parent, as before 1.17.1
sd=${DISCORD_STATE_DIR%/}
case $sd in */.claude/discord-agents/*) project_dir=${sd%/.claude/discord-agents/*}; [ ! -L "$sd" ] || { here=$PWD; cd -P "$sd" 2>/dev/null && sd=$PWD; cd "$here"; };; esac
case $sd in */bots/*) proj_state=${sd%/bots/*}; [ -n "${project_dir:-}" ] || IFS= read -r project_dir < "$proj_state/project";; *) proj_state=${sd%/*};; esac
```

Every `$DISCORD_STATE_DIR/..` becomes `$proj_state` (the 13 code sites in the measurement table); `tools/arc-events:27` becomes `cd "$project_dir"` after sourcing nothing (it is a tool: it gets the same three lines, inlined: tools do not source discord.sh, `arc-events` is run every minute and stays one process); the identity condition (:78) compares `"$project_dir" -ef "$CLAUDE_PROJECT_DIR"`; `migrate_project`'s `bot_project` is gone with it (Task 5). `refresh.sh:26-30` and `health.sh:100-103` (the `dirname` x3 of `DISCORD_STATE_DIR`) read the same way, in the wrapper's own helper (`state.sh`: `proj_of_state_dir`).

### 3.4 The move (`move_project <project>`), and who runs it

1. `p=$(cd -P "$project" && pwd -P)`, `k=$(proj_key "$p")`, `dst=$helpers/projects/$k`. `dst/project` exists and names another path -> refuse this project, say both paths ("a_b and a.b share one key"), leave it as it is; the other projects go on.
2. Under `dst.lock` (mkdir, as `pins.json.lock`; held > 10 s: skip, said): `mkdir -p dst/bots` (700); write `project` (temp + rename).
3. `config.env`, `peers.json`, `checkin/`: renamed into `dst/` when `dst/` has none; when `dst/` has one (a second machine sharing HOME moved first, or setup ran there), the old one is left, said.
4. Each bot dir `src/<bot>` (a directory with `.env`): **renamed** to `dst/bots/<bot>` (`perl -e 'rename ...'`, as `b_mv`, `bin/lib/bot.sh:190-196`), then `ln -s dst/bots/<bot> src/<bot>` at once (the window between the two is the rename and one `symlink(2)`; a hook that runs in it finds no state dir and exits 0, as for a non-bot; the bun server re-reads `access.json` per message and reopens `.env` only at a login). On another filesystem (`rename` fails with EXDEV): only when the bot has no live session (`live_sessions`), `cp -pR` to `dst/bots/.<bot>.part`, `diff -r` against the source, rename into place, `rm -rf` the source, then the link; with a live session it is left for the next start/update and said.
5. `src/hooks` (the 1.8-1.16 symlink): removed (Task 5). `src/.gitignore` stays while `src/` holds a symlink; `src/` itself goes in `unlink_old`.
6. `records/monitor/<bot>` of a manager of this project -> `records/monitor/<k>/<bot>`: the backend stopped first and started after, as `bot rename` does it (`bin/lib/bot.sh` rename: `--stop`, remember `was_stopped`, move, `--start` unless it was stopped); `scratch/<bot>` -> `scratch/<k>/<bot>` (a rename: 1.5 GB here, one filesystem).
7. `records/projects`: the project's line stays until every recorded project has moved; then the file is renamed `records/projects.1.16` (a downgrade's `health --all` still finds it; nothing reads it after 1.17.1).

**Who runs it:** `compat` (every `update`: the 1.16.0 `update` already runs `"$new/bin/claude-discord" compat` on the pulled code when it is >= 1.8.0, `install.sh:539-540`, so the very first `update` to 1.17.1 moves every recorded project on that machine); `setup` (its project, before its questions); the start (its project, when it still has the old shape: a person who pulled by hand and started a bot). Never a hook (a hook may not rename the state dir it runs under).

### 3.5 The transition (owner decision 3: per-bot symlinks)

Each job's `respawnFlags` freeze `--settings {"env":{"DISCORD_STATE_DIR":"<project>/.claude/discord-agents/<bot>"}}` (11 job records here); `claude respawn`, a daemon restart and a fleet claim all come back on that string. **Recommended: per-bot symlinks inside the kept `<project>/.claude/discord-agents/` directory**, `<bot> -> ~/.claude-discord/projects/<key>/bots/<bot>`, the `.gitignore` (`*`) kept beside them so `git status` stays clean. Alternative: `discord-agents` itself one symlink to `<key>/bots` (one link per project; but a symlink at `.claude/discord-agents` shows in `git status` as an untracked file in every project whose `.claude` is tracked, and `config.env`/`peers.json` would then be looked for under `bots/`).

What must accept the old path while a link stands:
- the hooks: 3.3 (both shapes);
- the plugin's bun server: it opens `$DISCORD_STATE_DIR/.env`, `access.json`, `inbox/` by path: the link resolves;
- `health`'s server count (`bin/lib/health.sh:193-230`) matches the environ's `DISCORD_STATE_DIR=<dir>` string: it counts a server under the new path OR the old one (`<project>/.claude/discord-agents/<bot>`, from `project`), or a respawned bot reads as `down` (a false `[down]` post to #bot-health-check for every moved bot until its next fresh start);
- `live_sessions` (`bin/lib/sessions.sh:7`) and the `--resume` job lookup (`bin/claude-discord:526-535`) grep `state.json` for `DISCORD_STATE_DIR\": \"$d\"`: both strings;
- the self-session guards (`bin/lib/bot.sh:307`, `:400`) use `-ef`: already both.

**`unlink_old <project>`** (run by `compat`, `setup`, the start, after the move): a link `src/<bot>` is removed when no `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/jobs/*/state.json` contains `DISCORD_STATE_DIR\": \"<src>/<bot>\"` (`grep -lF`, one call for all links of a project); `src/` itself (with its `.gitignore`) once it holds no link. A stopped job keeps its record (and so the link) until `claude rm <id>` or the bot's next start (`prune_dead_sessions` removes its stopped and done rows, 20 at a time): `compat` says which job holds which link.

**A relocated project** gets a new key by re-running `setup` there (it asks the questions again: the old key's `project` names a path that is gone, and `health --all` reports it as `project folder missing`, as today for a missing project). Adoption of the old key is not built (risk 7).

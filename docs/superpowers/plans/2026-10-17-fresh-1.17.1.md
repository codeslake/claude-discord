# 1.17.1: `f` never discards a conversation (the cswap loss of 2026-10-17)

**Why now.** On 2026-10-17 14:43Z the TUI showed cswap (lmd42) as `✕ STUCK 7h`; `f` proposed `claude-discord bot cswap
recover --fresh`, Junyong answered `y`, job 6bf81c6c was stopped and a fresh job started with no handoff. The session was
working: 181 user/assistant records since 07Z, the last at 14:37Z, on cross-session messages and the agentic-dev hub, not
on Discord. junyong-dev-bot restored it by hand (`claude stop` of the new job, `claude-discord --bg --name cswap --resume
<current id>`), and needed a second try because the live conversation was the takeover's id (3df5c3fb), not the job
record's (8f1ba77e). Reported in thread 1561027270150463599; the fix comes before the state move (now 1.18.0).

## Decisions (junyong-dev-bot, 14:49Z, on Junyong's delegation; dongyong22 informed in the thread)

1. The TUI's `f` and `F` send `recover` only, for `down` and `stale` alike. `--fresh` leaves the TUI entirely (the peer's
   "a separate choice with a red line" was offered; the smaller, safer form was agreed): a path to the discarding command
   one keystroke away is the defect.
2. `bot <bot> recover --fresh` refuses, before its question, while a transcript of the bot's session changed within the
   last 15 minutes; `claude stop <id>` by hand, then `recover`, is the way to discard anyway.
3. `health`: a transcript that moved within `stale_min` (15 min) reads `busy` ("it is working, not on Discord"), not
   `stale`, with no 4 h cap (cswap had 7 h). Accepted cost: a session looping for ever reads `busy` until its transcript
   stops moving; the README says so.
4. (the peer's addition) A session whose current id (`~/.claude/sessions/<pid>.json`, which follows `/clear` and a
   handover-and-takeover) differs from its job record's: `claude respawn` would bring the old conversation back, so
   `recover` stops the job and runs `--bg --name <bot> --resume <current id>` instead. Evidence for the rule: the peer's
   1.17.0 probe (a session cleared twice keeps one `sessions/<pid>.json` with its current sessionId) and `claude agents`
   showing 8f1ba77e for cswap while 3df5c3fb was live. Not probed: what `claude respawn` itself resumes; the rule does not
   depend on it (a differing id is never respawned).

## What the transcript is

`${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<key>/<sid>.jsonl`, `<key>` = the project's physical path with every
non-alphanumeric byte a dash (`proj_key`, now in `bin/claude-discord`, the rule 1.18.0's state move keys on too), `<sid>`
each name in `<bot dir>/plugin-sessions/` (the hooks' markers: since the 1.17.0 gate only the bot's own sessions, touched
per event, named by the id the session has NOW). `transcript_moved <bot dir> <minutes>` is one `find -mmin -N ( -name
a.jsonl -o ... ) -print -quit` (GNU and BSD), nothing when there is no marker (reads as "not moving": `recover --fresh`
and `stale` behave as in 1.17.0 for a bot whose hooks never ran).

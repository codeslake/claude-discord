# Boot, auto-recover and stale sessions (1.19.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** after a reboot, a daemon death or a lost server, every bot comes back without anyone typing `claude respawn`, and a session that is no bot any more is named as such.

**Architecture:** one new verb `boot` (every bot of this machine recovered once, through the existing `bot <bot> recover`), one new recover flag `--yes` (no terminal, no question: what boot and the monitor run), one new health list `stale_sessions` (plugin servers whose state dir is gone), and two new rules in the monitor's reducer (a `stale-session` finding; a `recover` action for a bot the channel was already told is down). The TUI learns the two new words. Nothing new is stored outside the monitor's state.json and the bot's recover.log.

**Tech Stack:** bash 3.2-compatible wrapper code, jq reducer, the two-file suite (`test-claude-discord.sh`, `test-install.sh`, `tests/suite-lib.sh`), Textual TUI.

**Spec:** this plan (the owner's three items, thread 1562133112190799924, 2026-10-20, with junyong-dev-bot's five review points folded in: one job per bot, egress through the host's reach, two passes before a recover, stale-session named with its job, negative controls).

## Global Constraints

- Each suite file finishes within 40 s wall time serially on lmd42 (CLAUDE.md); the core file was 34.7 s there at 1.18.0, so every new case goes into `test-install.sh`.
- Bash 3.2: no `mapfile` outside a `/proc` branch, no `${var,,}`, no `declare -A`; the wrapper must pass `bash -n` on macOS.
- Code and comments in English; Discord text as the monitor posts it stays in the reducer's two languages (ko default, en).
- A session never recovers its own bot (bot.sh exit 2): the monitor skips its manager's own entry.
- The monitor posts nothing but what the reducer decided; every new post kind goes through `post` and `apply` as the others do.
- Version: `.claude-plugin/plugin.json` 1.18.5 → 1.19.0; README names 1.19.0 at each new thing.

## Review Focus

- A reboot where `claude agents` lists every job with no pid: `boot` must respawn each once and never start a second session for a bot a person just started from the agents view (Task 2's `live_sessions` skip, tested with a listed pid).
- A `down` bot whose host also reads `noreach` in the same pass: no recover may run (Task 4, frozen host negative control).
- A `duplicate` bot: never recovered automatically (Task 4 negative control); `recover` without `--fresh` refuses two sessions anyway.
- A recover that keeps failing (exit 1 every time): one attempt per 30 minutes, each posted, never a loop within a pass (Task 4, the `recover_s` gate test).
- A server whose `DISCORD_STATE_DIR` is a path that exists only through the 1.18 link: it is a bot's server, not a stale one (Task 3 test with a linked old path).

**Interfaces:**
- Consumes: `stale_sessions` (Task 3), `bot <bot> recover --yes` (Task 1).
- Produces, in state.json: bot entries gain `recover_s`, `recover_rc`; entries keyed `<host>|stale|<job or pid>` with `bot: null`, `project: <state_dir>`, verdict `stale-session`; alerts records of kind `recover` (status `sent`/`failed` is the POST's, `detail` holds `exit <rc>`). Posts: `[recover] <bot> on <host> (<project>): ran <command> (exit 0)` or `[recover failed] ...: <command> exited <rc>`, no mention; `[stale-session] <state_dir> on <host>` as a finding with fix `claude stop <id>` (ssh-wrapped), owner mentioned as a host finding is. config.env `MONITOR_RECOVER=no` turns the action off (default yes).

Reducer rules (one place, as the others):
- `hold["stale-session"] = 0`; `fix` for `stale-session`: `claude stop <job>` (`kill <pid>` when the job is unknown), wrapped; `fix` for `down` becomes `cd <proj> && claude-discord bot <bot> recover` (the TUI's f), wrapped.
- `host_step`: each `$doc.stale_sessions[]` is observed as an entry `"\($r.host)|stale|\(.job // .pid)"` with `{host, name, project: .state_dir, home, owner_id: $mowner, pid, job}`; one that left the document is healed as crashed-project entries are (it already posts a recovery when `posted` is set, through `$healed`).
- A new output line `R<scope US key US command>` for each bot entry with `.bot != null`, verdict `down`, `.posted == "down"`, host reach ok, `$recover == "yes"`, `($now_s - (.recover_s // 0)) >= 1800`, and not `(host == "local" and bot == $manager)`; the command is `fix` with ` --yes` appended.
- `apply` takes result lines of kind `recover`: sets `.bots[key].recover_s = $now_s`, `.recover_rc`, and appends an alerts record `{kind: "recover", verdict: "down", status, detail: "exit <rc>", text}`.

`run_pass`: after the `O` loop, each `R` line runs its command through `run_cmd` (the `run_host` shape: setpgrp child, polled every step, `tick_check` every tick, cap `CLAUDE_DISCORD_MONITOR_RECOVER_CAP` default 90 s; local: `env <local_env> bash -c <command>`; remote: `ssh -o BatchMode=yes -o ConnectTimeout=8 <host> <command>`), logs `recover <key> rc=<n>`, posts the `[recover]`/`[recover failed]` payload (built by jq from `$recover_text` with the rc), and appends `bots US key US recover US down US <status> US <payload>` to `posts` so `apply` records it.

## Changed while implementing

- Task 1: the `--yes` case went into the core file beside the other recover cases (their fixtures live there; one run, a few ms).
- Task 2: `boot` decides "running" from one `claude agents --json` (a row with a pid, by name or pinned job, in the project's physical cwd) instead of `live_sessions` per bot (a row with an id but no pid counts as live there, which is exactly the case boot must recover). A recovered line says `recovered`; a failed one carries recover's last line. `boot` is a reserved bot name.
- Task 3: the scan lives in the `--all` block (the per-project `count_servers` setup runs after it); the parent walk reads `/proc/<pid>/stat` past the command name.
- Task 4: the tests went into the core file after the grouping block, reusing its monitor harness (rebuilding it in the install file would cost more than the cases); the grouping block runs with `MONITOR_RECOVER=no`, since its posted downs would now be recovered. The R line carries the remote command already quoted by the reducer (`cdp`, `qbot`); locally the shim runs with the project and bot as arguments. A stale-session recovery reads "the stale session is gone after <n>m". `apply` sets `recover_s`/`recover_rc` whatever became of the post. The reducer's direct test (`rpass`) passes the three new arguments.
